# Практична робота 7. Grafana, Ollama та перевірка AI-діагнозу

| Параметр | Значення |
|---|---|

Перед початком тримайте відкритими [platforms.md](platforms.md) (встановлення), [git.md](git.md) (власний репозиторій), [commands.md](commands.md) (пояснення команд та фіксованих імен). Це частини протоколу. Змінювати назву репозиторію можна; імена файлів, Compose-сервісів та внутрішні порти з прикладів збережіть, щоб спільні автотести знаходили потрібні компоненти.

## 1. Мета

Налаштувати Grafana й офіційний ollama/ollama, виконати локальний CPU inference та оцінити його за доказами контрольованого інциденту.

## 2. Очікувані результати навчання

- Власноруч створити конфігурації поточного етапу у своєму незмінному за місцем Git-проєкті.
- Перевірити працездатність за фактичними спостереженнями та пояснити межі висновку.

## 3. Правові й етичні межі

Працюємо лише з власним Compose-проєктом. Команди зупиняють або підключають тільки названі навчальні контейнери. Домашній роутер, мережу університету й чужі вузли не змінюємо. Секрети та реальні персональні журнали не додаємо в Git.

## 4. Необхідне середовище

Git, Bash, робочі Docker Linux engine і Compose v2+. Команди — у корені **власного** проєкту. В одному репозиторії залишаються всі ПР3–7; для наступної роботи не клонуйте новий проєкт. Шаблон дає лише TODO-файли, протоколи, перевірки та службові зафіксовані версії образів. Dockerfile й усі конфігурації заповнюєте ви. Група Compose називається autonomous-netlab незалежно від назви вашого репозиторію.

Маршрути ОС/VM і доступ до панелей — [platforms.md](platforms.md). У WSL зберігайте проєкт у файловій системі Ubuntu; на macOS — у власному каталозі, у Linux або окремій VM — у каталозі свого користувача. У новому терміналі повертайтеся в той самий корінь проєкту. Залиште Compose-групу `autonomous-netlab`: вона об’єднує всі його контейнери. Не задавайте інше значення `COMPOSE_PROJECT_NAME`. Скрипт `tests/compose.sh` вибирає файли поточного етапу; решту дій виконує Docker Compose.

## 6. Теоретичний блок

Grafana показує дані Prometheus. Наданий diagnose.py є тестовим API-клієнтом: він читає ваш ai-prompt.txt, збирає обмежені докази та надсилає запит локальному Ollama. Він не змінює мережу. Alertmanager працює незалежно; AI запускається окремим запитом до знімка події. JSON schema перевіряє форму, а правдивість причин перевіряє студент. Висновок insufficient_evidence теж може містити хибні твердження.

### Як пов’язані Grafana, LLM і сповіщення

Grafana звертається до Prometheus через datasource. Dashboard містить два часові ряди: успіх HTTP-проби та її тривалість у секундах. Ollama зберігає ваги у власному named volume та надає внутрішній HTTP API. Наданий diagnose.py — клієнт API: збирає малий знімок, читає вашу системну інструкцію й запитує аналіз. Він не надає моделі Docker socket, shell або функції застосування змін.

| Файл/параметр | Що ви налаштовуєте |
|---|---|
| grafana-datasource.yml | Ім’я, UID, тип і URL джерела Prometheus усередині мережі |
| grafana-provider.yml | Каталог, з якого Grafana читає dashboard JSON |
| grafana-dashboard.json | UID netlab, обидва PromQL вирази, заголовки й часовий інтервал |
| ai-prompt.txt | Інструкцію розділяти докази/гіпотези, не слухати інструкції з журналів і не виконувати дій |
| OLLAMA_NO_CLOUD=1 | Локальний режим; API не публікується на host-порт |
| MODEL у .env і ollama pull | Одне й те саме точне ім’я моделі; після зміни MODEL застосуйте up -d до toolbox |

Завантаження software-образу ollama/ollama і завантаження ваг qwen3:0.6b — різні операції. API version підтверджує лише роботу сервера. Технічний успіх AI-перевірки вимагає реальної відповіді /api/chat і валідної форми JSON. Правдивість тверджень модельних причин тест не встановлює: це можна самостійно дослідити за evidence.json; автоматичні бали не залежать від вгадування моделі.

У знімку є джерела E1–E3, цілі й часові мітки, а не всі журнали системи. У limited знімку вимірювань немає: обґрунтований висновок — причину ще не встановлено. Якщо модель упевнено назвала VLAN/DNS, поясніть, яких доказів для цього бракує. Не сприймайте її confidence як виміряну ймовірність. Alarm працює за правилами Prometheus й не очікує тексту LLM.

Ізольована Grafana використовує плагіни стандартного образу. Автовстановлення, автоматичні перевірки оновлень та зовнішній plugin admin вимкнені: у навчальній мережі немає доступу до каталогу Grafana. Перевірка підписів не вимикається; для неї використовується вбудований ключ. Рівень журналювання не знижується.

### Як читати JSON моделі

`analysis.json` містить технічні відомості запиту та поле `analysis` із діагностичною відповіддю. Нижче лише **приклад форми** цього поля, а не результат вашого запуску:

```json
{
  "assessment": "insufficient_evidence",
  "summary": "A service problem was reported, but no measurements are available.",
  "probable_causes": [],
  "evidence_ids": ["E1"],
  "recommended_checks": ["Collect HTTP probe results for the affected service."]
}
```

`assessment` допускає `hypothesis` (гіпотеза) або `insufficient_evidence` (доказів недостатньо). `summary` — короткий висновок; `probable_causes` — список можливих причин, `recommended_checks` — рекомендовані перевірки. `evidence_ids` посилається тільки на реально наявні E-ID в `evidence.json` цього знімка. У limited-досліді є лише E1 з повідомленням про проблему, тому E2 чи E3 вигадувати не можна. Порожній список причин допустимий. Поява E-ID у JSON підтверджує посилання на джерело, але ще не доводить, що висновок випливає з нього. У базовому prompt відповідь англійською; її переклад не є оцінюваною дією.

Заповніть compose.ai.yaml, файли provisioning, dashboard і власну інструкцію моделі за наведеним прикладом. Назва моделі має збігатися з MODEL у .env. ### P-03 Порівняти спостереження й гіпотези

Орієнтир: 30 хв активної роботи, включно з читанням кроку.

Відкрийте http://127.0.0.1:3000/d/netlab. Підпишіть джерело, ціль, час і одиниці панелей. У `results/checks/<run_id>/latest-incident.txt` прочитайте ідентифікатор знімка відмови. Самі файли `evidence.json`, `raw-response.json`, `analysis.json` та `report.md` містяться рівнем нижче: `results/checks/<run_id>/incidents/<incident_id>/`. Не плутайте короткий модельний `report.md` у каталозі інциденту з протоколом оцінювання в корені запуску. Зіставте відому дію stop backend-a з кожним твердженням моделі. Випишіть факти, гіпотези, хибні припущення та корисну наступну перевірку. В limited-аналізі немає метрик — причину не встановлено, навіть якщо модель її вигадала.


### P-04 Незалежність alarm і incident report

Орієнтир: 25 хв активної роботи, включно з читанням кроку.

Перевірка ALARM_WITHOUT_AI у повному check.sh виконується з вимкненою Ollama. Перевірте нові firing/resolved і роботу резерву: жоден з них не чекає LLM. У `report.md` поточного запуску знайдіть технічні результати AI_NORMAL, AI_INCIDENT, AI_LIMITED і ALARM_WITHOUT_AI. У відповідних збережених JSON знайдіть digest локальної моделі, версію Ollama, тривалість запиту та відповідь. Самостійно зіставте твердження з `evidence.json`: автопротокол не пише спростування помилок замість вас і не засвідчує правильність причини. Помилка моделі не знижує бал за аргументовано виконаний експеримент. Готовий текст моделі не замінює реального запуску.

### Група, образи та журнали

У Docker Desktop усі сервіси зібрані в autonomous-netlab. Тимчасові checks/probe належать цій самій групі й видаляються після перевірки. На хості Python не потрібний. У Compose задані номерні Docker Hub теги; tests/images.lock.json зберігає очікувані SHA-256, а IMAGES звіряє справжні RepoDigests. Невідповідність потребує узгодженого оновлення lock, а не зміни очікування задля зеленого тесту.

LOGS зберігає журнали й стани всіх потрібних сервісів у `results/checks/<run_id>/diagnostics/`. Після досліду сервіси мають знову працювати, без несподіваних traceback, fatal/error або OOM. Очікувана контрольована відмова позначається сценарієм і часовим вікном; помилки поза ним не приховуються. Started після restart ще не доводить готовності.

### Як прочитати результат команд

Очікується: після pull з’являється success; це означає наявність ваг локально, але ще не доводить inference. Повний тест дає 23/23, статус passed і machine_score=12: усної здачі немає. GRAFANA перевіряє обидва запити панелі та живу відповідь datasource, а не тільки /api/health. AI_NORMAL, AI_INCIDENT, AI_LIMITED виконують три реальні локальні запити, зберігають digest моделі, сирі відповіді, JSON та час. AI_OFF навмисно очікує unavailable. ALARM_WITHOUT_AI повторює відмову, нові firing/resolved та відновлення при вимкненій Ollama; потім запускає її назад. Помилка гіпотези моделі не є технічним збоєм inference: спростуйте її за доказами.

Усі команди запускайте по черзі; при ненульовому exit code не переходьте до commit. Стани: **passed** — очікування підтверджено; **failed** — отримано невідповідність; **blocked** — немає передумови; **skipped** — перевірку пропущено через обраний режим `--quick` або CI без моделі; **error** — збій перевірки, потрібен повтор і повідомлення викладачу. Тест продовжує незалежні перевірки, показує скільки завершено та які ще не виконані. Неповний запуск не дає остаточного машинного бала. Перевірки попередніх етапів є передумовами: їхня невідповідність також блокує остаточний бал поточної роботи; вони не дають прихованих додаткових балів. За повної перевірки невдалий критерій ПР3–6 отримує 0, успішні незалежні критерії зберігають свої бали.

`results/checks/latest-prNN.json` указує каталог останнього запуску; NN замініть номером роботи. У ньому `report.md` містить очікування, факти, підказки й критерії, `assessment.json` — машинні дані та SHA-256 тестів, `junit.xml` — файл результатів для автоматизованої перевірки CI. Якщо запуск зупинився ще до старту тестів через несправне середовище, створюються лише Markdown та JSON; відсутність JUnit у цьому випадку очікувана. Старі результати не перезаписуються. Тест також автоматично оновлює `docs/reports/pr07.md`. Додайте цей Markdown до commit; здайте тільки URL власного репозиторію. Тег `pr07` зберігає версію етапу; сам results/ не комітьте. Порожніх ручних reports/ у шаблоні немає. Детальний довідник команд — [commands.md](commands.md).

Перше check.sh збирає службовий контейнер перевірок з офіційного docker:cli та Python. Локальний Python не потрібний. Лише цей довірений тестовий контролер отримує Docker socket, щоб запускати проби, зупиняти й відновлювати ваш стенд. Навчальні вузли, Grafana та Ollama socket не отримують. Збірка тестової утиліти не замінює ваш Dockerfile.

## 9. Типові помилки й діагностика

| Симптом | Перевірка й наступна дія |
|---|---|
| Docker client є, server недоступний | Запустіть engine / перевірте WSL integration |
| TODO або помилка YAML | Перевірте, який файл заповнювали; tests/compose.sh pr07 config |
| Старий стан після редагування | Перезапустіть сервіс, що читає bind-mounted конфігурацію |
| Порт зайнятий | Змініть тільки host-порт у .env; container port не змінюйте |
| VM-панель не відкривається на хості | localhost VM і основної ОС різні; див. SSH-тунель у platforms.md |
| OOM або довгий inference | Перевірте logs/stats, MODEL і ресурси VM; запис не замінює локальну модель |

## 10. Завдання для самостійного виконання

**Необов’язкове поглиблення, без балів:** порівняйте дві локальні моделі за часом, пам’яттю та кількістю непідтверджених тверджень на тих самих доказах. Це не передумова наступної роботи.

Для самоперевірки назвіть один висновок, якого ваші дані не доводять, і наступну перевірку, яка змінила б рішення. Окремого файла чи додаткового домашнього налаштування не потрібно.

## 11. Зміст звіту

Звіт створюється **автоматично** командою tests/check.sh: results/checks/<run_id>/report.md. Спочатку оцінка/статус оцінювання, потім лічильники, критерії, деталі очікуваного й фактичного результату та підказки. Не створюйте окрему папку reports/ і не переписуйте помилки вручну. Тест автоматично копіює протокол у `docs/reports/pr07.md`; додайте цей файл до commit разом із конфігураціями й надішліть його до свого remote. Здайте тільки URL власного GitHub/GitLab-репозиторію. Тег `pr07` позначає версію роботи; окремі вкладення, SHA чи URL pipeline не потрібні. JSON та JUnit можна додати для діагностики. results/ не комітьте; якщо тест упав, спочатку виправте конфігурацію й отримайте новий звіт. Старий залишиться для порівняння.

ПР7 оцінюється автоматично на 12 балів. Модель може помилитися щодо причини: бали нараховуються за працездатність, збережені докази та коректну форму результату, а не вгадану гіпотезу.

## 12. Критерії оцінювання

| Критерій | Бали | Що перевіряється |
|---|---:|---|
| A01 | 3 | Grafana показує живі метрики на двох панелях |
| A02 | 3 | Офіційний Ollama виконав реальний локальний inference |
| A03 | 3 | Знімки інциденту, валідний JSON та наявні E-ID; хибні форми відхиляються |
| A04 | 3 | Сповіщення, резерв та відновлення працюють без LLM |

Разом 12 балів автоматично. Кожний критерій дає повну вагу після успіху всіх його перевірок або 0 при підтвердженій невідповідності. Неповна перевірка чи невиконані передумови блокують остаточний бал.

Бюджет: [20, 35, 30, 25] хв за кроками + 10 хв резерву = 120 хв. Читання, запис конфігурацій, експеримент і звіт включені. Це орієнтовний бюджет часу. Якщо активна робота перевищує 120 хв, повідомте викладачу, який крок потребував більше часу.

Після збереження результатів зупиніть поточний етап:

```bash
sh tests/compose.sh pr07 --profile monitoring --profile ai stop
```

`stop` зупиняє контейнери, зберігаючи їх і дані. Наступного разу виконайте команду `up -d` з цього протоколу. Щоб видалити контейнери й мережі, замініть `stop` на `down --remove-orphans`: файли проєкту та `results/` залишаться. Використовуйте номер **вже виконаної** роботи, щоб не читати майбутні TODO-файли. Параметр `down --volumes --remove-orphans` видаляє також named volume з вагами Ollama: модель доведеться завантажити повторно.

# Практична робота 6. Резервування HTTP-сервісу й сповіщення

| Параметр | Значення |
|---|---|
| Дисципліна | Проектування автономних мереж |
| Модуль | Один Git-проєкт на ПР3–7 |
| Опора на лекції | Docker, сегментація, HTTP-проби, резервування та спостережуваність; необхідний мінімум у §6 |
| Тривалість | 110 хв активних дій; пасивні завантаження окремо |
| Оцінювання | 10 балів; повністю за автотестами, без усної здачі |

Перед початком тримайте відкритими [platforms.md](platforms.md) (встановлення), [git.md](git.md) (власний репозиторій), [commands.md](commands.md) (пояснення команд та фіксованих імен). Це частини протоколу. Змінювати назву репозиторію можна; імена файлів, Compose-сервісів та внутрішні порти з прикладів збережіть, щоб спільні автотести знаходили потрібні компоненти.

## 1. Мета

Увімкнути primary/backup і незалежний маршрут сповіщення, перевірити відмову та повернення працездатності.

## 2. Очікувані результати навчання

- Власноруч створити конфігурації поточного етапу у своєму незмінному за місцем Git-проєкті.
- Перевірити працездатність за фактичними спостереженнями та пояснити межі висновку.

## 3. Правові й етичні межі

Працюємо лише з власним Compose-проєктом. Команди зупиняють або підключають тільки названі навчальні контейнери. Домашній роутер, мережу університету й чужі вузли не змінюємо. Секрети та реальні персональні журнали не додаємо в Git.

## 4. Необхідне середовище

Git, Bash, робочі Docker Linux engine і Compose v2+. Команди — у корені **власного** проєкту. В одному репозиторії залишаються всі ПР3–7; для наступної роботи не клонуйте новий проєкт. Шаблон дає лише TODO-файли, протоколи, перевірки та службові зафіксовані версії образів. Dockerfile й усі конфігурації заповнюєте ви. Група Compose називається autonomous-netlab незалежно від назви вашого репозиторію.

Маршрути ОС/VM і доступ до панелей — [platforms.md](platforms.md). У WSL зберігайте проєкт у файловій системі Ubuntu; на macOS — у власному каталозі, у Linux або окремій VM — у каталозі свого користувача. У новому терміналі повертайтеся в той самий корінь проєкту. Залиште Compose-групу `autonomous-netlab`: вона об’єднує всі його контейнери. Не задавайте інше значення `COMPOSE_PROJECT_NAME`. Скрипт `tests/compose.sh` вибирає файли поточного етапу; решту дій виконує Docker Compose.

## 5. Перевірка готовності

- [ ] Попередній тег працює; власні зміни збережено.
- [ ] .env не потрапляє в Git; тести й docs збережені.
- [ ] Записую активний час окремо від очікування завантажень.

## 6. Теоретичний блок

HAProxy активує backup після невдалих health checks основного backend. Це резервування HTTP, а не перебудова IP-маршрутів. Prometheus обчислює alert rule, Alertmanager надсилає webhook до тестового приймача events. for:10s не гарантує доставки за 10 секунд: є також scrape/evaluation/group_wait. Готовий event_sink.py є частиною автотестів; програмувати вебсервер студенту не потрібно.

### Резерв і повідомлення — різні механізми

У HAProxy `backup` позначає backend-b як резерв, який бере навантаження, коли primary не проходить health check. Prometheus незалежно перевіряє primary напряму: gateway може відповідати успішно через резерв, а probe primary уже 0. Правило PrimaryBackendUnavailable робить цю приховану для користувача відмову видимою оператору.

| Налаштування | Значення для досліду |
|---|---|
| server reserve ... backup | У нормі identity=backend-a, при відмові=backend-b |
| for: 10s | Умова повинна зберігатися перед переходом alert у firing |
| alerting.alertmanagers | Адреса Alertmanager, куди Prometheus передає alerts |
| group_by / group_wait | Групування за інцидентом і коротке очікування перед повідомленням |
| webhook url events:8001/alerts | Навчальний приймач сповіщень замість зовнішнього месенджера |
| send_resolved: true | Після відновлення приходить окреме resolved |

Тест читає received_at і startsAt, alertname та instance, тому старий запис від попереднього досліду не підходить. Не вимикайте gateway, коли завдання просить відмову backend-a: це інший експеримент. Повернення primary і resolved мають бути спостережені окремо, а не припущені після start.

Docker DNS має внутрішню адресу 127.0.0.11. resolvers docker_dns повторює розв’язання назв, а init-addr libc,none дозволяє початковий запуск без адреси вимкненого primary. Після його повернення DNS і health checks знову вводять сервер у роботу. Це важливо: статичне розв’язання лише під час старту могло зупинити HAProxy замість роботи через резерв.

## 7. Пакет вихідних даних

Шаблон містить `README.md`, протоколи в `docs/`, TODO-файли для заповнення, перевірки в `tests/` та `.gitlab-ci.yml`. `.env.example` задає спільні параметри, `tests/images.lock.json` — очікувані версії образів. Конфігурації створюєте ви за командами протоколу в цьому ж репозиторії; автотести перевіряють результат.

## 8. Хід роботи


### P-01 Передбачити реакцію

Орієнтир: 20 хв активної роботи, включно з читанням кроку.

Запишіть гіпотезу: при зупинці backend-a його probe стане 0, gateway лишиться доступним через backend-b, надійдуть firing і потім resolved. Зазначте спільну точку відмови gateway, яку backup не усуває.


### P-02 Написати конфігурації резерву й alerting

Орієнтир: 35 хв активної роботи, включно з читанням кроку.

Заповніть compose.resilience.yaml, alerts.yml, alertmanager.yml та файли backup. До попередніх HAProxy/Prometheus-файлів дописуємо лише нові блоки. Цей крок виконується один раз; при повторі приберіть власні дублікати.

```bash replay
cat > compose.resilience.yaml <<'EOF'
x-runtime: &runtime
  build:
    context: .
    args: {BASE_IMAGE: '${BASE_IMAGE}'}
  image: autonomous-netlab/toolbox:local
  working_dir: /workspace
  volumes: ['./:/workspace']
  mem_limit: 96m
  cpus: 0.5
  cap_drop: [ALL]
services:
  backend-b:
    <<: *runtime
    command: [python, -m, http.server, '8000', --bind, 0.0.0.0, --directory, site/backend-b]
    networks: [service]
  events:
    <<: *runtime
    profiles: [monitoring]
    command: [python, tests/event_sink.py]
    networks: [control]
  alertmanager:
    image: ${ALERTMANAGER_IMAGE}
    profiles: [monitoring]
    command: [--config.file=/etc/alertmanager/alertmanager.yml]
    volumes: [./config/alertmanager.yml:/etc/alertmanager/alertmanager.yml:ro]
    networks: [control]
    mem_limit: 64m
    cpus: 0.25
EOF
printf 'ok\n' > site/backend-b/health
printf 'backend-b\n' > site/backend-b/identity
cat >> config/haproxy.cfg <<'EOF'
  server reserve backend-b:8000 check inter 1s fall 2 rise 2 resolvers docker_dns init-addr libc,none backup
EOF
cat > config/alerts.yml <<'EOF'
groups:
  - name: netlab
    rules:
      - alert: PrimaryBackendUnavailable
        expr: probe_success{instance="http://backend-a:8000/health"} == 0
        for: 10s
        labels: {severity: warning}
        annotations: {summary: Primary HTTP backend probe failed}
      - alert: ProbeCollectionUnavailable
        expr: up{job="blackbox"} == 0
        for: 10s
        labels: {severity: warning}
EOF
cat >> config/prometheus.yml <<'EOF'
rule_files: [/etc/prometheus/alerts.yml]
alerting:
  alertmanagers:
    - static_configs:
        - targets: [alertmanager:9093]
EOF
cat > config/alertmanager.yml <<'EOF'
route:
  receiver: lab-events
  group_by: [alertname, instance]
  group_wait: 2s
  group_interval: 5s
  repeat_interval: 1h
receivers:
  - name: lab-events
    webhook_configs:
      - url: http://events:8001/alerts
        send_resolved: true
EOF
sh tests/compose.sh pr06 --profile monitoring up -d --build
sh tests/compose.sh pr06 restart -t 1 gateway prometheus
sh tests/check.sh pr06 --quick
sh tests/check.sh pr06
```


### P-03 Дослідити фактичну відмову

Орієнтир: 30 хв активної роботи, включно з читанням кроку.

Розгляньте FIRING, RESOLVED, FAILOVER і PRIMARY_RETURN у згенерованому report.md та assessment.json. Перевірте свіжі часові мітки, значення двох проб і відповідь backend-b. event_sink не має зв’язку з LLM; її ще не запускали. У разі переривання поверніть backend-a командою start перед повтором. Порівняйте параметри HAProxy й alerting: час до firing не є точним часом failover.


### P-04 Звіт і межа

Орієнтир: 15 хв активної роботи, включно з читанням кроку.

В автоматичному `report.md` знайдіть результати FIRING, FAILOVER, PRIMARY_RETURN та RESOLVED; зіставте їхні часові мітки й виберіть 2–4 докази відмови та відновлення. Для самоперевірки зробіть власний висновок, що станеться при відмові самого gateway: у схемі є резерв backend, але немає другого gateway. Автозвіт цього висновку не пише; нового експерименту чи ручного файла не потрібно. Після повернення health checks перевірте /identity: основний backend має знову обслуговувати запити.


Блоки Bash виконуйте послідовно в терміналі свого навчального середовища, з кореня проєкту. Після успішної повної перевірки відкрийте згенерований `report.md` і зафіксуйте етап командами нижче. Запитання «поясніть», «зіставте» й «випишіть» призначені для самоперевірки розуміння: окремого ручного звіту чи додаткового бала за них немає. У Git надсилайте конфігурації та автоматично створений `docs/reports/pr06.md`. Для здачі достатньо URL власного репозиторію; тег позначає виконаний етап.

```bash replay
printf 'pr06\n' > STAGE
git add .
git diff --cached --stat
git commit -m "pr06: complete machine configuration"
git tag pr06
git rev-parse HEAD
```

Після fork/import і clone origin уже вказує на вашу копію. Перевірте адресу й надішліть поточну гілку та тег:

```bash
git remote -v
git push -u origin HEAD
git push origin pr06
```

Якщо origin належить викладачу, виправте маршрут за git.md перед push. Для виправлення зробіть новий commit і тег pr06-v2; старий тег не пересувайте. Додаткова перевірка GitLab CI й обмеження її запуску пояснені в [README.md](../README.md#автоперевірки). Для здачі виконайте повний локальний тест; у ПР7 — разом із моделлю.

### Група, образи та журнали

У Docker Desktop усі сервіси зібрані в autonomous-netlab. Тимчасові checks/probe належать цій самій групі й видаляються після перевірки. На хості Python не потрібний. У Compose задані номерні Docker Hub теги; tests/images.lock.json зберігає очікувані SHA-256, а IMAGES звіряє справжні RepoDigests. Невідповідність потребує узгодженого оновлення lock, а не зміни очікування задля зеленого тесту.

LOGS зберігає журнали й стани всіх потрібних сервісів у `results/checks/<run_id>/diagnostics/`. Після досліду сервіси мають знову працювати, без несподіваних traceback, fatal/error або OOM. Очікувана контрольована відмова позначається сценарієм і часовим вікном; помилки поза ним не приховуються. Started після restart ще не доводить готовності.

### Як прочитати результат команд

Очікується: quick-перевірка показує 12/16 успішних і чотири пропущені експериментальні перевірки. Повний запуск дає 16/16 і 10/10. FAILOVER повертає backend-b, FIRING містить нове сповіщення PrimaryBackendUnavailable саме цього досліду, RESOLVED — його закриття, PRIMARY_RETURN знову повертає backend-a. Шлюз лишається доступним, хоча primary відмовив. Тест відновлює primary наприкінці досліду, також у разі помилки; якщо запуск перервано примусово, виконайте start backend-a і повторіть перевірку.

Усі команди запускайте по черзі; при ненульовому exit code не переходьте до commit. Стани: **passed** — очікування підтверджено; **failed** — отримано невідповідність; **blocked** — немає передумови; **skipped** — перевірку пропущено через обраний режим `--quick` або CI без моделі; **error** — збій перевірки, потрібен повтор і повідомлення викладачу. Тест продовжує незалежні перевірки, показує скільки завершено та які ще не виконані. Неповний запуск не дає остаточного машинного бала. Перевірки попередніх етапів є передумовами: їхня невідповідність також блокує остаточний бал поточної роботи; вони не дають прихованих додаткових балів. За повної перевірки невдалий критерій ПР3–6 отримує 0, успішні незалежні критерії зберігають свої бали.

`results/checks/latest-prNN.json` указує каталог останнього запуску; NN замініть номером роботи. У ньому `report.md` містить очікування, факти, підказки й критерії, `assessment.json` — машинні дані та SHA-256 тестів, `junit.xml` — файл результатів для автоматизованої перевірки CI. Якщо запуск зупинився ще до старту тестів через несправне середовище, створюються лише Markdown та JSON; відсутність JUnit у цьому випадку очікувана. Старі результати не перезаписуються. Тест також автоматично оновлює `docs/reports/pr06.md`. Додайте цей Markdown до commit; здайте тільки URL власного репозиторію. Тег `pr06` зберігає версію етапу; сам results/ не комітьте. Порожніх ручних reports/ у шаблоні немає. Детальний довідник команд — [commands.md](commands.md).

Перше check.sh збирає службовий контейнер перевірок з офіційного docker:cli та Python. Локальний Python не потрібний. Лише цей довірений тестовий контролер отримує Docker socket, щоб запускати проби, зупиняти й відновлювати ваш стенд. Навчальні вузли, Grafana та Ollama socket не отримують. Збірка тестової утиліти не замінює ваш Dockerfile.

## 9. Типові помилки й діагностика

| Симптом | Перевірка й наступна дія |
|---|---|
| Docker client є, server недоступний | Запустіть engine / перевірте WSL integration |
| TODO або помилка YAML | Перевірте, який файл заповнювали; tests/compose.sh pr06 config |
| Старий стан після редагування | Перезапустіть сервіс, що читає bind-mounted конфігурацію |
| Порт зайнятий | Змініть тільки host-порт у .env; container port не змінюйте |
| VM-панель не відкривається на хості | localhost VM і основної ОС різні; див. SSH-тунель у platforms.md |
| OOM або довгий inference | Перевірте logs/stats, MODEL і ресурси VM; запис не замінює локальну модель |

## 10. Завдання для самостійного виконання

**Необов’язкове поглиблення, без балів:** змініть інтервал health check, виміряйте час перемикання та поверніть початкову конфігурацію. Це не передумова наступної роботи.

Для самоперевірки назвіть один висновок, якого ваші дані не доводять, і наступну перевірку, яка змінила б рішення. Окремого файла чи додаткового домашнього налаштування не потрібно.

## 11. Зміст звіту

Звіт створюється **автоматично** командою tests/check.sh: results/checks/<run_id>/report.md. Спочатку оцінка/статус оцінювання, потім лічильники, критерії, деталі очікуваного й фактичного результату та підказки. Не створюйте окрему папку reports/ і не переписуйте помилки вручну. Тест автоматично копіює протокол у `docs/reports/pr06.md`; додайте цей файл до commit разом із конфігураціями й надішліть його до свого remote. Здайте тільки URL власного GitHub/GitLab-репозиторію. Тег `pr06` позначає версію роботи; окремі вкладення, SHA чи URL pipeline не потрібні. JSON та JUnit можна додати для діагностики. results/ не комітьте; якщо тест упав, спочатку виправте конфігурацію й отримайте новий звіт. Старий залишиться для порівняння.

ПР3–6 оцінюються автоматично по 10 балів, без усної здачі. Локальний звіт — самоперевірка; офіційна оцінка потребує контрольованого викладачем запуску.

## 12. Критерії оцінювання

| Критерій | Бали | Що перевіряється |
|---|---:|---|
| A01 | 2 | До відмови штатні проби успішні |
| A02 | 3 | Під час відмови gateway відповідає через backend-b |
| A03 | 3 | Отримано свіже firing сповіщення |
| A04 | 2 | Після повернення primary отримано свіже resolved |

Разом 10 балів. За кожний незалежний критерій зараховується зазначена кількість балів при успішній машинній перевірці; при підтвердженій невідповідності — 0 за цей критерій. Усної здачі й окремого бала за пояснення немає. Автопротокол зберігає технічні результати та підказки; власні міркування він не генерує. Збій інфраструктури означає повтор перевірки, а не автоматичний нуль. Офіційний автоматичний результат визначається перевіркою зданої версії, яку контролює викладач.

Бюджет: [20, 35, 30, 15] хв за кроками + 10 хв резерву = 110 хв. Читання, запис конфігурацій, експеримент і звіт включені. Це орієнтовний бюджет часу. Якщо активна робота перевищує 120 хв, повідомте викладачу, який крок потребував більше часу.

Після збереження результатів зупиніть поточний етап:

```bash
sh tests/compose.sh pr06 --profile monitoring stop
```

`stop` зупиняє контейнери, зберігаючи їх і дані. Наступного разу виконайте команду `up -d` з цього протоколу. Щоб видалити контейнери й мережі, замініть `stop` на `down --remove-orphans`: файли проєкту та `results/` залишаться. Використовуйте номер **вже виконаної** роботи, щоб не читати майбутні TODO-файли.

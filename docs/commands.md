# Як читати команди ПР3–7

Цей довідник пояснює спільні операції. Порядок виконання задає протокол конкретної роботи. Не запускайте всі приклади довідника як один скрипт. У командах `prNN` — позначення, яке треба замінити на `pr03`, `pr04`, `pr05`, `pr06` або `pr07`. Рядки протоколів із конкретним номером уже готові до виконання.

## Термінал, каталог і файли

Термінал виконує текстові команди. Bash — мова оболонки, якою написані блоки робіт. На Windows відкривайте **Ubuntu у WSL**, на macOS — Terminal і за потреби `bash`, у Linux/VM — термінал Linux. PowerShell потрібний лише для встановлення WSL: синтаксис наступних лабораторних розрахований на Bash.

Відкрийте каталог клонованого власного fork/import. `cd` змінює поточний каталог; шлях після нього має бути вашим фактичним шляхом. `pwd` показує поточний каталог; `ls -a` — його вміст разом із прихованими файлами. Очікується README.md, Dockerfile, compose.yaml, docs/, tests/ та .env.example. Якщо є ще один вкладений каталог із цими файлами, зайдіть у нього. Порожній TODO-Dockerfile ще не можна будувати.

```bash
pwd
ls -a
```

`#` починає коментар. Не вводьте символи запрошення `$` або `>` з чужих прикладів. Один рядок — одна команда; перевіряйте її результат перед наступною. Після команди `echo $?` показує код завершення: 0 — успіх, інше значення — помилка. Цю перевірку виконуйте одразу: кожна наступна команда замінює попередній код.

| Запис | Що відбувається | Очікуваний результат і навіщо |
|---|---|---|
| `cp .env.example .env` | Копіює спільні параметри у локальний файл | Повідомлення зазвичай немає; `ls -a` показує .env. Compose підставляє значення змінних із нього |
| `mkdir -p config` | Створює каталог, якщо його немає | Немає помилки; у шаблоні каталоги вже існують |
| `printf 'backend-a\n' > site/backend-a/identity` | Записує один рядок у файл | HTTP-сервіс поверне саме backend-a. `>` замінює попередній вміст |
| `cat > compose.yaml <<'EOF'` | Починає запис багаторядкового тексту | Усе до окремого рядка EOF стає вмістом файла. Лапки біля EOF зберігають `${...}` без підстановки оболонкою |
| `cat config/haproxy.cfg` | Читає файл без зміни | Можна перевірити збережений текст перед запуском |

Вводьте завершальний `EOF` без відступу. Якщо Bash показує друге запрошення `>`, блок ще не закритий. YAML чутливий до відступів: використовуйте пробіли, не Tab. Назви Linux-файлів розрізняють регістр. Не зберігайте `compose.yaml.txt` або `Dockerfile.txt`; увімкніть показ розширень у редакторі.

## Що саме запускає Docker

**Image** — файловий шаблон; **container** — його запущений екземпляр із власним станом. Dockerfile описує побудову образу toolbox. Compose описує сервіси, мережі та mounts. Один сервіс у цьому стенді має один контейнер. На ноутбуці працює Docker CLI, а Linux engine створює контейнери. У toolbox другий engine не потрібний.

| Інструкція ПР3 | Пояснення |
|---|---|
| `ARG BASE_IMAGE` / `FROM ${BASE_IMAGE}` | Приймає адресу базового upstream-образу й використовує його як основу |
| `RUN apk add --no-cache ...` | Під час build додає мережеві інструменти в Alpine-образ; --no-cache не зберігає кеш пакетного індексу |
| `WORKDIR /workspace` | Задає робочий каталог усередині контейнера |
| `ENV ...` | Задає змінні середовища процесам контейнера |
| `CMD ["sleep", "infinity"]` | Тримає toolbox запущеним, поки ви виконуєте в ньому інструменти через exec |
| `build.context: .` | Бере Dockerfile з поточного кореня проєкту |
| `volumes: ['./:/workspace']` | Відображає файли вашого проєкту в контейнері. Зміна цих файлів у контейнері видима на хості |
| `internal: true` | Створює ізольовану навчальну мережу; це не VLAN фізичного комутатора |
| `mem_limit`, `cpus` | Обмежують ресурси сервісу, але не визначають мінімум RAM усього ноутбука |

## Як читати повторювані блоки YAML

У ПР4 `x-host: &host` і в ПР6 `x-runtime: &runtime` задають спільні параметри контейнерів. Префікс `x-` позначає допоміжне розширення Compose; це не назва сервісу. `&host` дає фрагменту YAML ім’я, `*host` посилається на нього, а `<<: *host` додає його поля до поточного сервісу. Так однакові `build`, `image`, обмеження ресурсів і mount не треба переписувати для кожного вузла. Поля, явно записані в самому сервісі, уточнюють його налаштування: наприклад, `command` відрізняє HTTP-сервер від контейнера з `sleep`.

Збережіть відступи й імена як у протоколі. Якір діє в межах того самого YAML-файла: ПР6 оголошує власний `&runtime`, а не використовує `&host` з іншого файла. Остаточний результат злиття перевіряйте командою `sh tests/compose.sh prNN config`, замінивши `prNN` номером поточної роботи. Пояснення синтаксису — [офіційні YAML fragments у Compose](https://docs.docker.com/reference/compose-file/fragments/).

## Команди запуску та діагностики

`sh tests/compose.sh prNN ...` — звичайний Docker Compose із правильним для етапу списком файлів. Скрипт не генерує рішення. ПР3 бере compose.yaml; ПР4 додає compose.network.yaml; ПР5 — compose.monitoring.yaml; ПР6 — compose.resilience.yaml; ПР7 — compose.ai.yaml. Пізніші файли доповнюють попередні.

| Команда/частина | Що робить | Що має бути видно |
|---|---|---|
| `config` | Перевіряє YAML, підстановки .env та об’єднання файлів | Повна об’єднана конфігурація без помилки. Це ще не запуск |
| `up -d --build` | Будує власний toolbox, створює мережі й запускає контейнери у фоні | Built/Created/Started або Running; точні ID змінюються |
| `--profile monitoring up -d` | Додає сервіси з профілем monitoring | У ПР5 запускаються prometheus і blackbox; у ПР6 також alertmanager |
| `--profile ai up -d` | Додає Grafana й Ollama у ПР7 | Grafana/Ollama запущені; модель ще треба завантажити |
| `ps` | Показує контейнери поточного етапу | Потрібні сервіси — Up. Exited означає, що процес закінчився: читайте logs |
| `logs --tail 30 gateway` | Показує останні 30 рядків журналу gateway | Старт HAProxy або конкретна помилка конфігурації |
| `exec -T toolbox git --version` | Виконує команду в уже запущеному toolbox; -T вимикає псевдотермінал | git version ...; це Git у контейнері, ваші commits робіть Git у терміналі проєкту |
| `restart -t 1 prometheus` | Перезапускає процес для перечитування bind-mounted конфігурації | Restarted. Свіжі метрики з’являються після наступних scrape |
| `stop -t 1 backend-a` / `start backend-a` | Зупиняє/повертає лише primary | Перша дія створює контрольовану відмову; друга відновлює сервіс |
| `down` | Прибирає контейнери й мережі проєкту | Наступний up створює їх знову; файли проєкту збережені |
| `down --volumes` | Додатково прибирає named volumes | Ваги Ollama в цьому проєкті видаляються; знову потрібен pull моделі |

`curl -fsS URL` робить HTTP-запит: -f повертає помилку для HTTP-помилок, -s прибирає індикатор прогресу, -S залишає повідомлення про збій. `http://gateway:8080/identity` — ім’я сервісу й **внутрішній** порт у Docker-мережі. У браузері хоста використовується **опублікований** `http://127.0.0.1:8088/identity`. Це різні контексти доступу. `localhost` у контейнері означає цей контейнер, тому для Prometheus datasource вказується `http://prometheus:9090`, а не localhost.

## ПР3: як прочитати власні файли перед запуском

Це пояснення вже наявного кроку P-02, а не додаткове завдання. Повні файли й порядок команд наведено в pr03.md. У Bash `cat > Dockerfile <<'EOF'` записує наступні рядки у файл до окремого кінцевого `EOF`. Знак `>` замінює попередній вміст, тому спершу перевіряють `pwd` і назву файла. Лапки у початковому `'EOF'` вимикають підстановки Bash: `${BASE_IMAGE}` має лишитися текстом Dockerfile, а не зникнути через відсутню змінну оболонки. Кінцевий EOF пишуть без лапок і відступів. Очікування наступного рядка до EOF означає читання тексту оболонкою, а не build Docker. Це синтаксис Bash, який не копіюють буквально до PowerShell.

| Рядок вашого Dockerfile | Що робить саме у ПР3 | Як читати результат |
|---|---|---|
| ARG BASE_IMAGE | Параметр побудови з типовим значенням | Compose build.args може передати узгоджену основу |
| FROM | Вибирає базовий образ через BASE_IMAGE | Це початкова основа, не готовий toolbox викладача |
| LABEL | Додає навчальні метадані образу | Нічого не запускає й не встановлює |
| RUN apk add | Установлює Bash, curl, ip, ping і Git під час build | TOOLS перевіряє фактичні утиліти нового toolbox |
| WORKDIR | Задає початковий робочий каталог /workspace | Це шлях контейнера, пов’язаний із каталогом проєкту через mount |
| ENV | Задає початкові змінні для Python | Сам Python не запускається; писати програму для ПР3 не потрібно |
| CMD | Задає sleep infinity як типовий основний процес | Toolbox залишається запущеним для exec-проб |

`--no-cache` у рядку apk є параметром менеджера пакетів, а не загальним вимкненням кешу Docker. `PYTHONDONTWRITEBYTECODE=1` вимикає запис bytecode Python, `PYTHONUNBUFFERED=1` вимикає буферизацію його виводу. Редагування RUN не змінює старий образ: застосуйте вже наведене в P-02 `up -d --build`, а потім повторіть повну перевірку. Ручне встановлення утиліти всередині одного контейнера не робить Dockerfile відтворюваним.

У Compose `build.context: .` задає каталог матеріалів build, `build.args` передає параметри побудови, а `image` іменує локальний результат. `.env` використовується під час обчислення моделі; `environment` задає параметри створюваного контейнера. Це різні споживачі значень. MODEL у ПР3 лише резервує параметр подальшої роботи: він не встановлює Ollama та не завантажує модель. `working_dir` задає каталог процесу; `mem_limit` і `cpus` обмежують окремий toolbox, а не визначають загальний мінімум RAM ноутбука. `cap_drop` та `no-new-privileges` обмежують повноваження, але не скасовують наданого права запису в mount.

`./:/workspace` показує той самий каталог з боку хоста й контейнера. Запис або видалення підключеного файла з дозволеним записом змінює реальні файли проєкту. Файл поза mount може пережити stop/start того самого контейнера, але це не доказ збереження після його видалення. Саме тому PERSIST використовує свіжий marker і перестворення. Bind mount не є backup. Мережа control має internal: true: зовнішній curl із неї не є критерієм успішності ПР3, а отримання пакетів під час build відбувається в іншому контексті.

Після зміни Compose або environment застосуйте модель через up. Простий restart наявного контейнера не застосовує нові параметри створення. Restart може бути достатнім для перечитування файлу конфігурації, уже підключеного через bind mount, якщо саме так працює сервіс. Не плутайте ці два випадки. Config перевіряє обчислений опис; ps показує стан процесу; logs показує його вивід; exec перевіряє потрібну функцію всередині. Порожні logs для sleep очікувані, але не підтверджують утиліт чи mount. Ненульовий код завершення — підстава прочитати помилку до переходу далі.

## Імена: що можна змінити

Можна обрати довільні назву репозиторію на GitHub/GitLab, назву локального кореневого каталогу, власні Git name/email. Для каталогу використайте просту латиницю, цифри та дефіс, наприклад `network-lab`. Назва каталогу не змінює групу контейнерів: верхнє `name` у `compose.yaml` задає `autonomous-netlab`. Збережіть цю групу й не задавайте інше `COMPOSE_PROJECT_NAME`.

Поки навчаєтеся, збережіть ці імена, бо це контракт спільних перевірок:

| Частина | Точні імена |
|---|---|
| Сервіси | toolbox, employee, guest, admin, gateway, backend-a, backend-b, prometheus, blackbox, events, alertmanager, grafana, ollama |
| Файли | Dockerfile, compose.yaml, compose.network.yaml, compose.monitoring.yaml, compose.resilience.yaml, compose.ai.yaml |
| Каталоги | config/, site/admin/, site/backend-a/, site/backend-b/, tests/, docs/ |
| Вміст /identity | admin, backend-a або backend-b відповідно до сервісу; це перевіряється буквально |
| Штатні HTTP targets | http://gateway:8080/health та http://backend-a:8000/health |
| Метадані | STAGE містить pr03…pr07; Git tag — pr03…pr07 або виправлення prNN-v2 |
| Grafana / alert | UID netlab; datasource netlab-prometheus; alert PrimaryBackendUnavailable |

Внутрішні порти, імена мереж/сервісів і назви конфігурацій залиште як у протоколі. Вільні **host-порти** можна змінювати через .env; PUBLIC_PORT впливає на адресу браузера, але не на gateway:8080 усередині стенда. Не редагуйте tests/, щоб приховати помилку: читайте expected/observed/hint та виправляйте власну конфігурацію. Якщо викладач оновив тести, отримайте весь узгоджений набір, а не окремий випадковий файл.

## Теги образів і `<none>`

У .env.example і Compose використовуються номерні теги, наприклад haproxy:3.4.7-alpine. Очікуваний digest зберігається окремо у tests/images.lock.json; IMAGES перевіряє реальний вміст. LTS обрано там, де продукт має таку гілку (HAProxy, Prometheus), для решти — актуальний стабільний реліз. Оновлення виконує викладач разом із повторним проходженням протоколів; теги RC/dev не використовуються.

Docker може показати тег `<none>` для образу, завантаженого за digest: локальний RepoTag не обов’язково створюється. Він також може показати старий образ без тега після rebuild. Щоб розрізнити ці випадки, перегляньте `docker image ls --digests` та `docker image inspect IMAGE_ID`: RepoDigests ідентифікує upstream-вміст, RepoTags — локальні назви. Не видаляйте образ лише через `<none>`, поки не перевірили, які контейнери його використовують. Це не ознака старої версії.

## Автоматичний звіт і здача

`sh tests/check.sh prNN` перевіряє поточний стенд і створює новий `results/checks/<run_id>/report.md`. На початку — автоматична оцінка /10 для ПР3–6 або /12 для ПР7, потім лічильники, критерії, очікування, фактичні дані та дії для виправлення. Відкрийте цей файл як Markdown у редакторі. Поруч `assessment.json` і, після запуску основного набору перевірок, `junit.xml`. Якщо попередня перевірка середовища зупинилася через несправний Docker, відсутній `.env` чи помилку збірки утиліти, створюються лише Markdown і JSON; JUnit у такому випадку ще немає. Файл latest-prNN.json указує останній запуск, старі звіти зберігаються.

`--quick` у ПР4–7 пропускає частину експериментів і дає частковий звіт. У ПР3 набір перевірок із цим параметром збігається з повним. Для здачі всіх робіт використовуйте команду **без `--quick`**, як наведено в протоколі. `failed` означає перевірену невідповідність; `blocked` — немає передумови; `error` — перевірка не змогла завершитися; `skipped` — пропуск за явно обраним режимом. Остаточний машинний бал при неповних перевірках не визначається. Попередні етапи є передумовами: їхні невдалі перевірки блокують остаточний бал поточної ПР, не утворюючи додаткових критеріїв бала. ПР7 отримує остаточний числовий бал лише за повної перевірки, включно з реальним локальним inference; quick/CI без моделі залишається частковим результатом.

Папки порожніх ручних reports/ немає. Тест автоматично оновлює `docs/reports/prNN.md`, де NN — номер роботи; додайте цей файл до commit разом із конфігураціями й надішліть гілку та тег. Для здачі потрібен тільки URL власного репозиторію: викладач відкриє файли та протокол там. Окремі вкладення, SHA та URL pipeline не потрібні. `results/` не входить у Git. Для ПР7 використайте збережені snapshots та відповіді моделі для самостійної перевірки тверджень. Локальний звіт можна змінити вручну, тому остаточне автоматичне оцінювання потребує контрольованого викладачем запуску; чужий зелений pipeline чи Markdown сам по собі цього не доводить.

Офіційні довідники: [Compose model](https://docs.docker.com/compose/intro/compose-application-model/), [Git book](https://git-scm.com/book/en/v2), [Prometheus releases](https://prometheus.io/download/). 

LOGS перевіряє всі сервіси після повернення штатного стану й зберігає їхні журнали та exit codes у `results/checks/<run_id>/diagnostics/`. Очікувані повідомлення інциденту мають часові вікна. Traceback або аварійне завершення не ігноруються лише тому, що HTTP-проба колись пройшла.

Якщо помилка журналу є підтвердженим наслідком проваленого критерію (наприклад, HTTP503 при відсутньому backup), вона зберігається з посиланням на FAILOVER і не знімає бали вдруге. Це explained_failure, а не успішна робота резерву. Сторонні помилки, несправний кінцевий стан або недоступні журнали блокують остаточну оцінку.

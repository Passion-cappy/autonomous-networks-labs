# Практична робота 5. HTTP-моніторинг через Prometheus і Blackbox

Перед початком тримайте відкритими [platforms.md](platforms.md) (встановлення), [git.md](git.md) (власний репозиторій), [commands.md](commands.md) (пояснення команд та фіксованих імен). Це частини протоколу. Змінювати назву репозиторію можна; імена файлів, Compose-сервісів та внутрішні порти з прикладів збережіть, щоб спільні автотести знаходили потрібні компоненти.

## 1. Мета

Створити конфігурації моніторингу й відрізнити відмову HTTP-проби від відмови збору метрик.

## 2. Очікувані результати навчання

- Власноруч створити конфігурації поточного етапу у своєму незмінному за місцем Git-проєкті.
- Перевірити працездатність за фактичними спостереженнями та пояснити межі висновку.

## 3. Правові й етичні межі

Працюємо лише з власним Compose-проєктом. Команди зупиняють або підключають тільки названі навчальні контейнери. Домашній роутер, мережу університету й чужі вузли не змінюємо. Секрети та реальні персональні журнали не додаємо в Git.

## 4. Необхідне середовище

Git, Bash, робочі Docker Linux engine і Compose v2+. Команди — у корені **власного** проєкту. В одному репозиторії залишаються всі ПР3–7; для наступної роботи не клонуйте новий проєкт. Шаблон дає лише TODO-файли, протоколи, перевірки та службові зафіксовані версії образів. Dockerfile й усі конфігурації заповнюєте ви. Група Compose називається autonomous-netlab незалежно від назви вашого репозиторію.

Маршрути ОС/VM і доступ до панелей — [platforms.md](platforms.md). У WSL зберігайте проєкт у файловій системі Ubuntu; на macOS — у власному каталозі, у Linux або окремій VM — у каталозі свого користувача. У новому терміналі повертайтеся в той самий корінь проєкту. Залиште Compose-групу `autonomous-netlab`: вона об’єднує всі його контейнери. Не задавайте інше значення `COMPOSE_PROJECT_NAME`. Скрипт `tests/compose.sh` вибирає файли поточного етапу; решту дій виконує Docker Compose.

## 6. Теоретичний блок

Blackbox виконує HTTP-запит до цілі. Prometheus збирає результат: probe_success — успіх проби, up — успіх scrape exporter. Вони можуть бути відповідно 0 і 1. Відсутня серія не дорівнює нулю. probe_duration_seconds є тривалістю HTTP-проби, а не ICMP RTT чи пропускною здатністю.

**Метрика** — виміряне числове значення з назвою. **Часова серія** — послідовність його значень у часі з певним набором міток. **Label** — мітка, наприклад `instance="http://gateway:8080/health"`: вона вказує, до якої цілі належить результат. **Scrape** — одне опитування джерела метрик Prometheus; **exporter** — компонент, який їх віддає. **PromQL** — мова запитів Prometheus. У полі запиту введіть `probe_success`: отримаєте окремі рядки для цілей, а не один загальний стан мережі. Фільтр `probe_success{instance="http://gateway:8080/health"}` залишає тільки потрібну ціль. Усі ці дії використовують уже налаштовані у роботі дані.

### Шлях вимірювання

Prometheus кожні кілька секунд звертається до Blackbox. Blackbox виконує HTTP-запит до переданої target й повертає метрики. Тому можливі два різні збої: ціль не відповідає (probe_success=0 при up=1) або Prometheus не може отримати відповідь самого exporter (up=0). Стенд не вимірює packet loss лише на підставі HTTP-помилки.

| Параметр | Навіщо він у вашій конфігурації |
|---|---|
| http_ok у blackbox.yml | Ім’я модуля HTTP-перевірки; params.module у Prometheus має збігатися |
| metrics_path: /probe | Просить exporter перевірити ціль, а не лише віддати власні метрики |
| __param_target | Передає справжню адресу цілі Blackbox |
| instance | Зберігає адресу перевірюваного сервісу як label часової серії |
| __address__: blackbox:9115 | Спрямовує scrape до exporter замість самої HTTP-цілі |
| scrape_interval / evaluation_interval | Частота збору й перевірки правил; це різні операції |

У браузері відкрийте Prometheus /targets: рядок Up означає успішний scrape exporter. У запиті probe_success перевірте instance обох цілей. Вкладка Graph покаже зміну в часі; старі серії можуть ще бути видимі після зміни target. Саме тому автотести звіряють timestamp реального зразка, а не лише значення 0/1.

## 7. Пакет вихідних даних

Шаблон містить `README.md`, протоколи в `docs/`, TODO-файли для заповнення, перевірки в `tests/` та `.gitlab-ci.yml`. `.env.example` задає спільні параметри, `tests/images.lock.json` — очікувані версії образів. Конфігурації створюєте ви за командами протоколу в цьому ж репозиторії; автотести перевіряють результат.

## 8. Хід роботи


### P-01 Знайти джерело й цілі

Орієнтир: 20 хв активної роботи, включно з читанням кроку.

На своїй схемі позначте позицію Blackbox, адреси gateway:8080/health і backend-a:8000/health. Перед запуском поясніть, що саме може довести кожна проба й чому її джерело відрізняється від employee.


### P-02 Написати конфігурації

Орієнтир: 35 хв активної роботи, включно з читанням кроку.

Заповніть compose.monitoring.yaml, config/prometheus.yml та blackbox.yml. Контейнери готові з Docker Hub, але їхні мережі, цілі й зв’язки налаштовуєте ви.

```bash replay
cat > compose.monitoring.yaml <<'EOF'
services:
  prometheus:
    image: ${PROMETHEUS_IMAGE}
    profiles: [monitoring]
    command: [--config.file=/etc/prometheus/prometheus.yml, --storage.tsdb.retention.time=2h, --storage.tsdb.retention.size=64MB]
    volumes: [./config/prometheus.yml:/etc/prometheus/prometheus.yml:ro, ./config/alerts.yml:/etc/prometheus/alerts.yml:ro]
    ports: ['127.0.0.1:${PROMETHEUS_PORT:-9090}:9090']
    networks: [control]
    mem_limit: 256m
    cpus: 0.5
  blackbox:
    image: ${BLACKBOX_IMAGE}
    profiles: [monitoring]
    command: [--config.file=/etc/blackbox/config.yml]
    volumes: [./config/blackbox.yml:/etc/blackbox/config.yml:ro]
    networks: [control, service]
    mem_limit: 64m
    cpus: 0.25
EOF
cat > config/blackbox.yml <<'EOF'
modules:
  http_ok:
    prober: http
    timeout: 3s
    http:
      valid_status_codes: [200]
      preferred_ip_protocol: ip4
EOF
cat > config/prometheus.yml <<'EOF'
global:
  scrape_interval: 5s
  evaluation_interval: 5s
scrape_configs:
  - job_name: blackbox
    metrics_path: /probe
    params: {module: [http_ok]}
    static_configs:
      - targets: [http://gateway:8080/health, http://backend-a:8000/health]
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target
      - source_labels: [__param_target]
        target_label: instance
      - target_label: __address__
        replacement: blackbox:9115
EOF
sh tests/compose.sh pr05 --profile monitoring up -d
sh tests/check.sh pr05 --quick
```


### P-03 Хибний порт при працездатному exporter

Орієнтир: 30 хв активної роботи, включно з читанням кроку.

Відкрийте http://127.0.0.1:9090/targets. У Prometheus виконайте probe_success та up{job="blackbox"}. Повний тест нижче тимчасово змінює лише порт backend-a з 8000 на 8999, перезапускає prometheus і чекає свіжої проби. Очікуйте probe_success=0 та up=1. Перевірте gateway вручну й журнал backend-a: сервіс не зупиняли. Тест повертає точні початкові байти конфігурації наприкінці досліду, також у разі помилки, перезапускає Prometheus і повторює проби. Перевірте кожний факт у звіті.

```bash replay
sh tests/check.sh pr05
```


### P-04 Короткий звіт

Орієнтир: 15 хв активної роботи, включно з читанням кроку.

За автоматичним report.md порівняйте таблицю «норма—хибний порт—відновлення»: probe_success, up, ручне спостереження. Поясніть наступну перевірку при up=0. Не видавайте стару серію за поточний результат.


Блоки Bash виконуйте послідовно в терміналі свого навчального середовища, з кореня проєкту. Після успішної повної перевірки відкрийте згенерований `report.md` і зафіксуйте етап командами нижче. Запитання «поясніть», «зіставте» й «випишіть» призначені для самоперевірки розуміння: окремого ручного звіту чи додаткового бала за них немає. У Git надсилайте конфігурації та автоматично створений `docs/reports/pr05.md`. Для здачі достатньо URL власного репозиторію; тег позначає виконаний етап.

```bash replay
printf 'pr05\n' > STAGE
git add .
git diff --cached --stat
git commit -m "pr05: complete machine configuration"
git tag pr05
git rev-parse HEAD
```

Після fork/import і clone origin уже вказує на вашу копію. Перевірте адресу й надішліть поточну гілку та тег:

```bash

git push -u origin HEAD
git push origin pr05
```

Якщо origin належить викладачу, виправте маршрут за git.md перед push. Для виправлення зробіть новий commit і тег pr05-v2; старий тег не пересувайте. Додаткова перевірка GitLab CI й обмеження її запуску пояснені в [README.md](../README.md#автоперевірки). Для здачі виконайте повний локальний тест; у ПР7 — разом із моделлю.

### Група, образи та журнали

У Docker Desktop усі сервіси зібрані в autonomous-netlab. Тимчасові checks/probe належать цій самій групі й видаляються після перевірки. На хості Python не потрібний. У Compose задані номерні Docker Hub теги; tests/images.lock.json зберігає очікувані SHA-256, а IMAGES звіряє справжні RepoDigests. Невідповідність потребує узгодженого оновлення lock, а не зміни очікування задля зеленого тесту.

LOGS зберігає журнали й стани всіх потрібних сервісів у `results/checks/<run_id>/diagnostics/`. Після досліду сервіси мають знову працювати, без несподіваних traceback, fatal/error або OOM. Очікувана контрольована відмова позначається сценарієм і часовим вікном; помилки поза ним не приховуються. Started після restart ще не доводить готовності.

### Як прочитати результат команд

Очікується: quick-перевірка показує 12/14 успішних, дві експериментальні пропущено. У P-03 повний запуск дає 14/14 і 10/10. У METRICS обидві штатні probe_success=1 та exporter up=1; WRONG_PORT дає probe_success=0 при up=1; METRICS_RESTORED знову дає штатні значення. Порівнюється час реального останнього scrape, старий результат не зараховується. up=1 означає доступність exporter, а не HTTP-цілі. Якщо up=0, спочатку перевірте адресу blackbox:9115 та мережу control.

Усі команди запускайте по черзі; при ненульовому exit code не переходьте до commit. Стани: **passed** — очікування підтверджено; **failed** — отримано невідповідність; **blocked** — немає передумови; **skipped** — перевірку пропущено через обраний режим `--quick` або CI без моделі; **error** — збій перевірки, потрібен повтор і повідомлення викладачу. Тест продовжує незалежні перевірки, показує скільки завершено та які ще не виконані. Неповний запуск не дає остаточного машинного бала. Перевірки попередніх етапів є передумовами: їхня невідповідність також блокує остаточний бал поточної роботи; вони не дають прихованих додаткових балів. За повної перевірки невдалий критерій ПР3–6 отримує 0, успішні незалежні критерії зберігають свої бали.

`results/checks/latest-prNN.json` указує каталог останнього запуску; NN замініть номером роботи. У ньому `report.md` містить очікування, факти, підказки й критерії, `assessment.json` — машинні дані та SHA-256 тестів, `junit.xml` — файл результатів для автоматизованої перевірки CI. Якщо запуск зупинився ще до старту тестів через несправне середовище, створюються лише Markdown та JSON; відсутність JUnit у цьому випадку очікувана. Старі результати не перезаписуються. Тест також автоматично оновлює `docs/reports/pr05.md`. Додайте цей Markdown до commit; здайте тільки URL власного репозиторію. Тег `pr05` зберігає версію етапу; сам results/ не комітьте. Порожніх ручних reports/ у шаблоні немає. Детальний довідник команд — [commands.md](commands.md).

Перше check.sh збирає службовий контейнер перевірок з офіційного docker:cli та Python. Локальний Python не потрібний. Лише цей довірений тестовий контролер отримує Docker socket, щоб запускати проби, зупиняти й відновлювати ваш стенд. Навчальні вузли, Grafana та Ollama socket не отримують. Збірка тестової утиліти не замінює ваш Dockerfile.

## 9. Типові помилки й діагностика

| Симптом | Перевірка й наступна дія |
|---|---|
| Docker client є, server недоступний | Запустіть engine / перевірте WSL integration |
| TODO або помилка YAML | Перевірте, який файл заповнювали; tests/compose.sh pr05 config |
| Старий стан після редагування | Перезапустіть сервіс, що читає bind-mounted конфігурацію |
| Порт зайнятий | Змініть тільки host-порт у .env; container port не змінюйте |
| VM-панель не відкривається на хості | localhost VM і основної ОС різні; див. SSH-тунель у platforms.md |
| OOM або довгий inference | Перевірте logs/stats, MODEL і ресурси VM; запис не замінює локальну модель |

## 10. Завдання для самостійного виконання

**Необов’язкове поглиблення, без балів:** порівняйте up, probe_success і probe_duration_seconds під час тимчасово недоступного exporter. Це не передумова наступної роботи.

Для самоперевірки назвіть один висновок, якого ваші дані не доводять, і наступну перевірку, яка змінила б рішення. Окремого файла чи додаткового домашнього налаштування не потрібно.

## 11. Зміст звіту

Звіт створюється **автоматично** командою tests/check.sh: results/checks/<run_id>/report.md. Спочатку оцінка/статус оцінювання, потім лічильники, критерії, деталі очікуваного й фактичного результату та підказки. Не створюйте окрему папку reports/ і не переписуйте помилки вручну. Тест автоматично копіює протокол у `docs/reports/pr05.md`; додайте цей файл до commit разом із конфігураціями й надішліть його до свого remote. Здайте тільки URL власного GitHub/GitLab-репозиторію. Тег `pr05` позначає версію роботи; окремі вкладення, SHA чи URL pipeline не потрібні. JSON та JUnit можна додати для діагностики. results/ не комітьте; якщо тест упав, спочатку виправте конфігурацію й отримайте новий звіт. Старий залишиться для порівняння.

ПР3–6 оцінюються автоматично по 10 балів, без усної здачі. Локальний звіт — самоперевірка; офіційна оцінка потребує контрольованого викладачем запуску.

## 12. Критерії оцінювання

| Критерій | Бали | Що перевіряється |
|---|---:|---|
| A01 | 2 | Prometheus збирає результати Blackbox |
| A02 | 2 | Обидві штатні HTTP-цілі мають успішну пробу |
| A03 | 3 | Хибний порт дає probe_success=0 при up=1 |
| A04 | 3 | Після виправлення штатна проба знову успішна |

Разом 10 балів. За кожний незалежний критерій зараховується зазначена кількість балів при успішній машинній перевірці; при підтвердженій невідповідності — 0 за цей критерій. Усної здачі й окремого бала за пояснення немає. Автопротокол зберігає технічні результати та підказки; власні міркування він не генерує. Збій інфраструктури означає повтор перевірки, а не автоматичний нуль. Офіційний автоматичний результат визначається перевіркою зданої версії, яку контролює викладач.

Бюджет: [20, 35, 30, 15] хв за кроками + 10 хв резерву = 110 хв. Читання, запис конфігурацій, експеримент і звіт включені. Це орієнтовний бюджет часу. Якщо активна робота перевищує 120 хв, повідомте викладачу, який крок потребував більше часу.

Після збереження результатів зупиніть поточний етап:

```bash
sh tests/compose.sh pr05 --profile monitoring stop
```

`stop` зупиняє контейнери, зберігаючи їх і дані. Наступного разу виконайте команду `up -d` з цього протоколу. Щоб видалити контейнери й мережі, замініть `stop` на `down --remove-orphans`: файли проєкту та `results/` залишаться. Використовуйте номер **вже виконаної** роботи, щоб не читати майбутні TODO-файли.

# Практична робота 4. Сегментована мережа й перевірка доступу

| Параметр | Значення |
|---|---|
| Дисципліна | Проектування автономних мереж |
| Модуль | Один Git-проєкт на ПР3–7 |
| Опора на лекції | Docker, сегментація, HTTP-проби, резервування та спостережуваність; необхідний мінімум у §6 |
| Тривалість | 110 хв активних дій; пасивні завантаження окремо |
| Оцінювання | 10 балів; повністю за автотестами, без усної здачі |

Перед початком тримайте відкритими [platforms.md](platforms.md) (встановлення), [git.md](git.md) (власний репозиторій), [commands.md](commands.md) (пояснення команд та фіксованих імен). Це частини протоколу. Змінювати назву репозиторію можна; імена файлів, Compose-сервісів та внутрішні порти з прикладів збережіть, щоб спільні автотести знаходили потрібні компоненти.

## 1. Мета

Побудувати мережу «працівник—гість—сервіс», перевірити матрицю HTTP-доступу та виявити витік через зайвий інтерфейс.

## 2. Очікувані результати навчання

- Власноруч створити конфігурації поточного етапу у своєму незмінному за місцем Git-проєкті.
- Перевірити працездатність за фактичними спостереженнями та пояснити межі висновку.

## 3. Правові й етичні межі

Працюємо лише з власним Compose-проєктом. Команди зупиняють або підключають тільки названі навчальні контейнери. Домашній роутер, мережу університету й чужі вузли не змінюємо. Секрети та реальні персональні журнали не додаємо в Git.

## 4. Необхідне середовище

Git, Bash, робочі Docker Linux engine і Compose v2+. Команди — у корені **власного** проєкту. В одному репозиторії залишаються всі ПР3–7; для наступної роботи не клонуйте новий проєкт. Шаблон дає лише TODO-файли, протоколи, перевірки та службові зафіксовані версії образів. Dockerfile й усі конфігурації заповнюєте ви. Група Compose називається autonomous-netlab незалежно від назви вашого репозиторію.

Маршрути ОС/VM і доступ до панелей — [platforms.md](platforms.md). У WSL зберігайте проєкт у файловій системі Ubuntu; на macOS — у власному каталозі, у Linux або окремій VM — у каталозі свого користувача. У новому терміналі повертайтеся в той самий корінь проєкту. Залиште Compose-групу `autonomous-netlab`: вона об’єднує всі його контейнери. Не задавайте інше значення `COMPOSE_PROJECT_NAME`. Скрипт `tests/compose.sh` вибирає файли поточного етапу; решту дій виконує Docker Compose.

## 5. Перевірка готовності

- [ ] Попередній тег працює; власні зміни збережено.
- [ ] .env не потрапляє в Git; тести й docs збережені.
- [ ] Записую активний час окремо від очікування завантажень.

## 6. Теоретичний блок

Контейнери однієї bridge-мережі можуть спілкуватися в її межах. Gateway передає HTTP до backend; це не загальне IP-forwarding і не модель VLAN. DNS-відмова не доводить ізоляцію. Гостьову пробу виконуємо також за фактичними IP admin, включно з додатковим інтерфейсом у разі витоку.

### Яку мережу ми будуємо

Працівник employee і admin поділяють work. Гість guest має окрему guest. Gateway приєднаний до обох клієнтських мереж та серверної мережі service; він приймає HTTP на 8080 й передає запит backend-a:8000. Admin не є backend HAProxy: до нього дозволено звертатися лише з work. Toolbox лишається точкою керування; інтернет із internal-мереж не є навчальним критерієм.

| Джерело → ціль | Очікування | Причина |
|---|---|---|
| employee → gateway:8080/identity | backend-a | Є спільна work, gateway проксіює до сервера |
| guest → gateway:8080/identity | backend-a | Gateway приймає публічний HTTP і з guest |
| employee → admin:8000/identity | admin | Обидва у work |
| guest → будь-яка IP admin, TCP 8000 | з’єднання не встановлюється | Admin не має guest-інтерфейсу |

`site/.../health` — простий HTTP-файл перевірки життя; `identity` повертає ідентичність відповідача. Python http.server віддає файли з визначеного каталогу; HAProxy не створює ці файли. Health check використовує HEAD /health: сервер повертає заголовки без тіла, тому завершення перевірки не обриває запис тіла GET. Це не вимкнення журналювання. У haproxy.cfg `frontend` слухає 8080, `default_backend` вибирає групу серверів, а `server primary backend-a:8000 check` задає ціль та health check. Розділення Docker bridge мереж демонструє сегментацію; це не конфігурація VLAN фізичного комутатора й не повна маршрутизація автономної системи.

Docker DNS має внутрішню адресу 127.0.0.11. resolvers docker_dns повторює розв’язання назв, а init-addr libc,none дозволяє початковий запуск без адреси вимкненого primary. Після його повернення DNS і health checks знову вводять сервер у роботу. Це важливо: статичне розв’язання лише під час старту могло зупинити HAProxy замість роботи через резерв.

## 7. Пакет вихідних даних

Шаблон містить `README.md`, протоколи в `docs/`, TODO-файли для заповнення, перевірки в `tests/` та `.gitlab-ci.yml`. `.env.example` задає спільні параметри, `tests/images.lock.json` — очікувані версії образів. Конфігурації створюєте ви за командами протоколу в цьому ж репозиторії; автотести перевіряють результат.

## 8. Хід роботи


### P-01 Передбачити політику

Орієнтир: 15 хв активної роботи, включно з читанням кроку.

Намалюйте employee—work—admin; guest—guest; gateway—work/guest/service/control; backend-a—service. Перед запуском запишіть чотири очікування: employee→gateway дозволено, employee→admin дозволено, guest→gateway дозволено, guest→admin заборонено. У всіх випадках це HTTP і конкретний порт.


### P-02 Створити мережевий шар

Орієнтир: 40 хв активної роботи, включно з читанням кроку.

Заповніть compose.network.yaml, config/haproxy.cfg та HTTP-файли. x-host і << повторно використовують спільні параметри лише в цьому YAML. tests/compose.sh додає файли відповідного етапу до одного Compose-проєкту; він не створює топологію.

```bash replay
cat > compose.network.yaml <<'EOF'
x-host: &host
  build:
    context: .
    args: {BASE_IMAGE: '${BASE_IMAGE}'}
  image: autonomous-netlab/toolbox:local
  working_dir: /workspace
  volumes: ['./:/workspace']
  mem_limit: 96m
  cpus: 0.5
  cap_drop: [ALL]
  security_opt: [no-new-privileges:true]
services:
  employee:
    <<: *host
    networks: [work]
  guest:
    <<: *host
    networks: [guest]
  admin:
    <<: *host
    command: [python, -m, http.server, '8000', --bind, 0.0.0.0, --directory, site/admin]
    networks: [work]
  backend-a:
    <<: *host
    command: [python, -m, http.server, '8000', --bind, 0.0.0.0, --directory, site/backend-a]
    networks: [service]
  gateway:
    image: ${HAPROXY_IMAGE}
    volumes: [./config/haproxy.cfg:/usr/local/etc/haproxy/haproxy.cfg:ro]
    ports: ['127.0.0.1:${PUBLIC_PORT:-8088}:8080']
    networks: [work, guest, service, control]
    mem_limit: 64m
    cpus: 0.5
    cap_drop: [ALL]
networks:
  work: {internal: true}
  guest: {internal: true}
  service: {internal: true}
EOF
cat > config/haproxy.cfg <<'EOF'
global
  log stdout format raw local0
  nbthread 1
defaults
  mode http
  log global
  timeout connect 2s
  timeout client 5s
  timeout server 5s
resolvers docker_dns
  nameserver dns 127.0.0.11:53
  timeout resolve 1s
  timeout retry 1s
  hold valid 1s
frontend public
  bind :8080
  default_backend application
backend application
  option httpchk HEAD /health
  server primary backend-a:8000 check inter 1s fall 2 rise 2 resolvers docker_dns init-addr libc,none
EOF
printf 'ok\n' > site/admin/health
printf 'admin\n' > site/admin/identity
printf 'ok\n' > site/backend-a/health
printf 'backend-a\n' > site/backend-a/identity
sh tests/compose.sh pr04 up -d --build
sh tests/check.sh pr04 --quick
```


### P-03 Перевірити й спростувати ізоляцію

Орієнтир: 30 хв активної роботи, включно з читанням кроку.

Зіставте EMP_PUBLIC, EMP_ADMIN, GUEST_PUBLIC та GUEST_DENIED у report.md з матрицею. Повний тест нижче тимчасово підключає admin до guest і переконується, що незалежна проба відхиляє витік, а потім відновлює ізоляцію. Саме очікувана відмова тут є успішним негативним контролем.

```bash replay
sh tests/check.sh pr04
```


### P-04 Пояснення й версія

Орієнтир: 15 хв активної роботи, включно з читанням кроку.

Зіставте мережеві зв’язки з §6 з очікуванням/фактом у report.md та доказом GUEST_LEAK. Поясніть, чому тест лише однієї work-IP міг би пропустити інший інтерфейс. Змініть PUBLIC_PORT у .env на вільний локальний порт, застосуйте up -d та перевірте gateway з браузера/SSH-тунелю; внутрішня матриця не повинна змінитися. Поверніть порт перед здачею, якщо він вільний.


Блоки Bash виконуйте послідовно в терміналі свого навчального середовища, з кореня проєкту. Після успішної повної перевірки відкрийте згенерований `report.md` і зафіксуйте етап командами нижче. Запитання «поясніть», «зіставте» й «випишіть» призначені для самоперевірки розуміння: окремого ручного звіту чи додаткового бала за них немає. У Git надсилайте конфігурації та автоматично створений `docs/reports/pr04.md`. Для здачі достатньо URL власного репозиторію; тег позначає виконаний етап.

```bash replay
printf 'pr04\n' > STAGE
git add .
git diff --cached --stat
git commit -m "pr04: complete machine configuration"
git tag pr04
git rev-parse HEAD
```

Після fork/import і clone origin уже вказує на вашу копію. Перевірте адресу й надішліть поточну гілку та тег:

```bash
git remote -v
git push -u origin HEAD
git push origin pr04
```

Якщо origin належить викладачу, виправте маршрут за git.md перед push. Для виправлення зробіть новий commit і тег pr04-v2; старий тег не пересувайте. Додаткова перевірка GitLab CI й обмеження її запуску пояснені в [README.md](../README.md#автоперевірки). Для здачі виконайте повний локальний тест; у ПР7 — разом із моделлю.

### Група, образи та журнали

У Docker Desktop усі сервіси зібрані в autonomous-netlab. Тимчасові checks/probe належать цій самій групі й видаляються після перевірки. На хості Python не потрібний. У Compose задані номерні Docker Hub теги; tests/images.lock.json зберігає очікувані SHA-256, а IMAGES звіряє справжні RepoDigests. Невідповідність потребує узгодженого оновлення lock, а не зміни очікування задля зеленого тесту.

LOGS зберігає журнали й стани всіх потрібних сервісів у `results/checks/<run_id>/diagnostics/`. Після досліду сервіси мають знову працювати, без несподіваних traceback, fatal/error або OOM. Очікувана контрольована відмова позначається сценарієм і часовим вікном; помилки поза ним не приховуються. Started після restart ще не доводить готовності.

### Як прочитати результат команд

Очікується: спочатку quick-перевірка підтверджує 11/12 перевірок; LEAK_CONTROL пропущено, тому остаточного бала ще немає. У P-03 повна перевірка дає 12/12 і 10/10. EMP_PUBLIC і GUEST_PUBLIC повертають backend-a, EMP_ADMIN — admin. GUEST_DENIED перевіряє TCP за фактичними IP admin: відсутнього DNS-імені недостатньо. LEAK_CONTROL тимчасово додає admin до guest, вимагає виявлення GUEST_LEAK, прибирає лише доданий інтерфейс і перевіряє відновлення ізоляції. Власні початкові помилки тест не виправляє.

Усі команди запускайте по черзі; при ненульовому exit code не переходьте до commit. Стани: **passed** — очікування підтверджено; **failed** — отримано невідповідність; **blocked** — немає передумови; **skipped** — перевірку пропущено через обраний режим `--quick` або CI без моделі; **error** — збій перевірки, потрібен повтор і повідомлення викладачу. Тест продовжує незалежні перевірки, показує скільки завершено та які ще не виконані. Неповний запуск не дає остаточного машинного бала. Перевірки попередніх етапів є передумовами: їхня невідповідність також блокує остаточний бал поточної роботи; вони не дають прихованих додаткових балів. За повної перевірки невдалий критерій ПР3–6 отримує 0, успішні незалежні критерії зберігають свої бали.

`results/checks/latest-prNN.json` указує каталог останнього запуску; NN замініть номером роботи. У ньому `report.md` містить очікування, факти, підказки й критерії, `assessment.json` — машинні дані та SHA-256 тестів, `junit.xml` — файл результатів для автоматизованої перевірки CI. Якщо запуск зупинився ще до старту тестів через несправне середовище, створюються лише Markdown та JSON; відсутність JUnit у цьому випадку очікувана. Старі результати не перезаписуються. Тест також автоматично оновлює `docs/reports/pr04.md`. Додайте цей Markdown до commit; здайте тільки URL власного репозиторію. Тег `pr04` зберігає версію етапу; сам results/ не комітьте. Порожніх ручних reports/ у шаблоні немає. Детальний довідник команд — [commands.md](commands.md).

Перше check.sh збирає службовий контейнер перевірок з офіційного docker:cli та Python. Локальний Python не потрібний. Лише цей довірений тестовий контролер отримує Docker socket, щоб запускати проби, зупиняти й відновлювати ваш стенд. Навчальні вузли, Grafana та Ollama socket не отримують. Збірка тестової утиліти не замінює ваш Dockerfile.

## 9. Типові помилки й діагностика

| Симптом | Перевірка й наступна дія |
|---|---|
| Docker client є, server недоступний | Запустіть engine / перевірте WSL integration |
| TODO або помилка YAML | Перевірте, який файл заповнювали; tests/compose.sh pr04 config |
| Старий стан після редагування | Перезапустіть сервіс, що читає bind-mounted конфігурацію |
| Порт зайнятий | Змініть тільки host-порт у .env; container port не змінюйте |
| VM-панель не відкривається на хості | localhost VM і основної ОС різні; див. SSH-тунель у platforms.md |
| OOM або довгий inference | Перевірте logs/stats, MODEL і ресурси VM; запис не замінює локальну модель |

## 10. Завдання для самостійного виконання

**Необов’язкове поглиблення, без балів:** намалюйте шлях пакета гість → gateway → backend; поясніть, чому цей стенд не доводить VLAN/firewall-набуття. Це не передумова наступної роботи.

Для самоперевірки назвіть один висновок, якого ваші дані не доводять, і наступну перевірку, яка змінила б рішення. Окремого файла чи додаткового домашнього налаштування не потрібно.

## 11. Зміст звіту

Звіт створюється **автоматично** командою tests/check.sh: results/checks/<run_id>/report.md. Спочатку оцінка/статус оцінювання, потім лічильники, критерії, деталі очікуваного й фактичного результату та підказки. Не створюйте окрему папку reports/ і не переписуйте помилки вручну. Тест автоматично копіює протокол у `docs/reports/pr04.md`; додайте цей файл до commit разом із конфігураціями й надішліть його до свого remote. Здайте тільки URL власного GitHub/GitLab-репозиторію. Тег `pr04` позначає версію роботи; окремі вкладення, SHA чи URL pipeline не потрібні. JSON та JUnit можна додати для діагностики. results/ не комітьте; якщо тест упав, спочатку виправте конфігурацію й отримайте новий звіт. Старий залишиться для порівняння.

ПР3–6 оцінюються автоматично по 10 балів, без усної здачі. Локальний звіт — самоперевірка; офіційна оцінка потребує контрольованого викладачем запуску.

## 12. Критерії оцінювання

| Критерій | Бали | Що перевіряється |
|---|---:|---|
| A01 | 2 | Працівник отримує відповідь публічного сервісу |
| A02 | 2 | Працівник має доступ до admin |
| A03 | 2 | Гість має доступ до публічного сервісу |
| A04 | 2 | Гість не має доступу до admin за фактичними IP |
| A05 | 2 | Тест відхиляє доданий guest-інтерфейс і приймає виправлення |

Разом 10 балів. За кожний незалежний критерій зараховується зазначена кількість балів при успішній машинній перевірці; при підтвердженій невідповідності — 0 за цей критерій. Усної здачі й окремого бала за пояснення немає. Автопротокол зберігає технічні результати та підказки; власні міркування він не генерує. Збій інфраструктури означає повтор перевірки, а не автоматичний нуль. Офіційний автоматичний результат визначається перевіркою зданої версії, яку контролює викладач.

Бюджет: [15, 40, 30, 15] хв за кроками + 10 хв резерву = 110 хв. Читання, запис конфігурацій, експеримент і звіт включені. Це орієнтовний бюджет часу. Якщо активна робота перевищує 120 хв, повідомте викладачу, який крок потребував більше часу.

Після збереження результатів зупиніть поточний етап:

```bash
sh tests/compose.sh pr04 stop
```

`stop` зупиняє контейнери, зберігаючи їх і дані. Наступного разу виконайте команду `up -d` з цього протоколу. Щоб видалити контейнери й мережі, замініть `stop` на `down --remove-orphans`: файли проєкту та `results/` залишаться. Використовуйте номер **вже виконаної** роботи, щоб не читати майбутні TODO-файли.

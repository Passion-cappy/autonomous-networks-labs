# Практична робота 3. Git-проєкт і власне контейнерне середовище

| Параметр | Значення |
|---|---|
| Дисципліна | Проектування автономних мереж |
| Модуль | Один Git-проєкт на ПР3–7 |
| Опора на лекції | Docker, сегментація, HTTP-проби, резервування та спостережуваність; необхідний мінімум у §6 |
| Тривалість | 120 хв активних дій; пасивні завантаження окремо |
| Оцінювання | 10 балів; повністю за автотестами, без усної здачі |

Перед початком тримайте відкритими [platforms.md](platforms.md) (встановлення), [git.md](git.md) (власний репозиторій), [commands.md](commands.md) (пояснення команд та фіксованих імен). Це частини протоколу. Змінювати назву репозиторію можна; імена файлів, Compose-сервісів та внутрішні порти з прикладів збережіть, щоб спільні автотести знаходили потрібні компоненти.

## 1. Мета

Створити власну копію шаблону на GitHub або GitLab і власноруч побудувати toolbox з Dockerfile; довести збереження файлів після перестворення контейнера.

## 2. Очікувані результати навчання

- Власноруч створити конфігурації поточного етапу у своєму незмінному за місцем Git-проєкті.
- Перевірити працездатність за фактичними спостереженнями та пояснити межі висновку.

## 3. Правові й етичні межі

Працюємо лише з власним Compose-проєктом. Команди зупиняють або підключають тільки названі навчальні контейнери. Домашній роутер, мережу університету й чужі вузли не змінюємо. Секрети та реальні персональні журнали не додаємо в Git.

## 4. Необхідне середовище

Git, Bash, робочі Docker Linux engine і Compose v2+. Команди — у корені **власного** проєкту. В одному репозиторії залишаються всі ПР3–7; для наступної роботи не клонуйте новий проєкт. Шаблон дає лише TODO-файли, протоколи, перевірки та службові зафіксовані версії образів. Dockerfile й усі конфігурації заповнюєте ви. Група Compose називається autonomous-netlab незалежно від назви вашого репозиторію.

Маршрути ОС/VM і доступ до панелей — [platforms.md](platforms.md). У WSL зберігайте проєкт у файловій системі Ubuntu; на macOS — у власному каталозі, у Linux або окремій VM — у каталозі свого користувача. У новому терміналі повертайтеся в той самий корінь проєкту. Залиште Compose-групу `autonomous-netlab`: вона об’єднує всі його контейнери. Не задавайте інше значення `COMPOSE_PROJECT_NAME`. Скрипт `tests/compose.sh` вибирає файли поточного етапу; решту дій виконує Docker Compose.

## 5. Перевірка готовності

- [ ] Маю доступ до студентського шаблону й можливість установити Git і Docker за [platforms.md](platforms.md). Власну копію шаблону створюю та клоную в P-01.
- [ ] .env не потрапляє в Git; тести й docs збережені.
- [ ] Записую активний час окремо від очікування завантажень.

## 6. Теоретичний блок

Dockerfile задає побудову образу; Compose визначає контейнери й мережі. Ми використовуємо готовий офіційний Python лише як основу, а свій toolbox будуємо самі. Bind mount зберігає робочі файли поза життєвим циклом контейнера. Git фіксує конфігурації; тег позначає конкретний commit. Ваги моделі, .env і результати runtime у Git не додаємо.

### Як влаштована основа проєкту

У ПР3 лише один контейнер toolbox. Ваші файли лежать на хості в каталозі проєкту й одночасно видимі в /workspace контейнера. Тому видалення toolbox не видаляє Dockerfile або конфігурації. Зміна файла не змінює вже зібраний image: після зміни RUN потрібний build, після зміни Compose — up, а після зміни bind-mounted конфігурації сервісу може знадобитися restart.

| Файл | Ваше рішення | Де перевірити |
|---|---|---|
| Dockerfile | Базовий образ, мережеві утиліти, робочий каталог, процес sleep | TOOLS показує версії, RESTART перевіряє запуск |
| compose.yaml | Побудова toolbox, mount, мережа control, обмеження ресурсів | CONFIG/SAFETY, потім PERSIST |
| .env | Локальні refs образів і host-порти з .env.example | config показує підстановки; .env не потрапляє в Git |
| .gitignore | надані правила виключення результатів/секретів | git status не показує results/ та .env |

Перед P-04 виконайте локальні git config за [git.md](git.md) у вже клонованому репозиторії. На першому commit не повинно бути Author identity unknown.

## 7. Пакет вихідних даних

Шаблон містить `README.md`, протоколи в `docs/`, TODO-файли для заповнення, перевірки в `tests/` та `.gitlab-ci.yml`. `.env.example` задає спільні параметри, `tests/images.lock.json` — очікувані версії образів. Конфігурації створюєте ви за командами протоколу в цьому ж репозиторії; автотести перевіряють результат.

## 8. Хід роботи

### P-01 Встановлення й власний Git-репозиторій

Орієнтир: 45 хв активної роботи, включно з читанням кроку.

Спочатку виконайте **один** маршрут встановлення з [platforms.md](platforms.md). Windows: Ubuntu WSL2 + Docker Desktop integration; окрема Ubuntu VM у Hyper-V є альтернативою. Усі команди нижче виконуються в **Bash навчального середовища**, не в PowerShell. На macOS відкрийте Terminal і виконайте `bash`. У Linux/VM використовуйте її термінал.

Перевірте інструменти **на хості**, де зберігатиметься клон:

```bash
git --version
docker version
docker compose version
docker info --format '{{.OSType}}'
```

| Команда | Очікуваний результат | Якщо інакше |
|---|---|---|
| `git --version` | `git version ...` | Завершіть встановлення Git за platforms.md |
| `docker version` | Розділи Client **і Server** | Запустіть Docker; у WSL перевірте integration з вашою Ubuntu |
| `docker compose version` | Версія сучасного Compose plugin | Установіть plugin або оновіть Desktop; не підставляйте старий `docker-compose` |
| `docker info ...` | `linux` | Переключіть Desktop на Linux containers або виправте доступ до Engine |

Поки Docker Server недоступний, не переходьте до побудови образу. Мережеве отримання пакетів та образів потрібне під час встановлення й build; toolbox після запуску матиме внутрішню мережу.

Відкрийте **посилання на студентський шаблон, надане викладачем**: сторінку проєкту з `README.md`, `docs/` та `tests/`, а не профіль користувача. На GitLab створіть Fork у власному просторі імен; на GitHub — Import repository того самого шаблону. Покрокові екрани та офіційні інструкції є в [git.md](git.md). Не клонуйте викладацький шаблон замість власної копії й не створюйте другий `.git` через `git init`.

Скопіюйте HTTPS URL **свого** fork/import. У команді замініть `ВАШ_HTTPS_URL` цією адресою; `network-lab` — довільна назва локального каталогу:

```bash
git clone ВАШ_HTTPS_URL network-lab
cd network-lab
pwd
ls -a
git remote -v
git status --short
```

Очікується: корінь вашої копії, файли `Dockerfile`, `compose.yaml`, `.env.example`, каталоги `docs/`, `tests/` і прихований `.git`. `origin` указує на вашу копію; порожній вивід `status --short` означає, що робочих змін ще немає. TODO у файлах — правильний початковий стан. Усі наступні команди запускайте саме з цього каталогу. Якщо URL належить викладачу, спершу виправте `origin` за git.md.

Налаштуйте автора commit **лише для цього репозиторію**. Замініть обидва приклади своїми даними; email може бути приватною адресою, наданою Git-сервісом:

```bash
git config user.name "Ваше ім’я та прізвище"
git config user.email "ваша-адреса@example.com"
git config --get user.name
git config --get user.email
```

Останні дві команди мають показати ваші значення. Це підпис commit, а не вхід до GitHub/GitLab. Порядок автентифікації для HTTPS пояснено в git.md; токени в URL або звіт не вставляйте.

### P-02 Створити Dockerfile і Compose

Орієнтир: 35 хв активної роботи, включно з читанням кроку.

Створіть `.env` зі спільних параметрів і заповніть дві TODO-заготовки. `cat > файл` замінює його вміст, а завершальний `EOF` вводиться окремим рядком без відступів. Цей початковий блок не повторюють поверх конфігурацій уже виконаних ПР4–7. Докладне пояснення кожної інструкції є в [commands.md](commands.md).

```bash replay
cp .env.example .env
cat > Dockerfile <<'EOF'
ARG BASE_IMAGE=python:3.15.2-alpine
FROM ${BASE_IMAGE}
LABEL edu.netlab.owner="autonomous-netlab"
RUN apk add --no-cache bash curl iproute2 iputils git
WORKDIR /workspace
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
CMD ["sleep", "infinity"]
EOF
cat > compose.yaml <<'EOF'
name: ${COMPOSE_PROJECT_NAME:-autonomous-netlab}
services:
  toolbox:
    build:
      context: .
      args: {BASE_IMAGE: '${BASE_IMAGE}'}
    image: autonomous-netlab/toolbox:local
    working_dir: /workspace
    volumes: ['./:/workspace']
    environment: {MODEL: '${MODEL:-qwen3:0.6b}'}
    networks: [control]
    mem_limit: 128m
    cpus: 0.5
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]
networks:
  control: {internal: true}
EOF
sh tests/compose.sh pr03 config
sh tests/compose.sh pr03 up -d --build
sh tests/compose.sh pr03 ps
sh tests/compose.sh pr03 logs --tail 30 toolbox
```

| Дія | Очікуваний результат і значення | Якщо інакше |
|---|---|---|
| `cp .env.example .env` | Зазвичай без виводу; з’явився локальний `.env` | Перевірте `pwd`, `ls -a` та назву `.env.example` |
| `config` | Об’єднаний опис без помилки: toolbox, внутрішня control, mount до `/workspace`, підставлений BASE_IMAGE | Виправте назви, відступи й `.env`; це ще не запуск |
| `up -d --build` | Образ побудовано, toolbox створено й запущено | Прочитайте останню помилку build; після зміни RUN перебудуйте образ |
| `ps` | Toolbox має стан Up/Running | Прочитайте `logs`; Exited означає завершення головного процесу |
| `logs --tail 30 toolbox` | Для `sleep infinity` журнал може бути порожній | Аварійне завершення або traceback потребує виправлення; порожній журнал не доводить наявності інструментів |

`internal: true` ізолює control від зовнішньої мережі. Toolbox підключений тільки до control; `cap_drop: [ALL]` забирає capabilities, а `no-new-privileges:true` обмежує набуття нових привілеїв. RAM та CPU мають додатні ліміти; наведені 128 MiB і 0,5 CPU — параметри toolbox, а не вимога до всієї оперативної пам’яті ноутбука. Ці властивості перевіряє SAFETY. Параметр MODEL тут лише резервує значення для наступної роботи: Ollama й модель зараз не запускаються.

Перевірте всі чотири утиліти **в уже запущеному toolbox**:

```bash replay
sh tests/compose.sh pr03 exec -T toolbox curl --version
sh tests/compose.sh pr03 exec -T toolbox ip -V
sh tests/compose.sh pr03 exec -T toolbox ping -V
sh tests/compose.sh pr03 exec -T toolbox git --version
```

Очікуються версії curl, iproute2, iputils і Git без помилки. `exec -T toolbox` запускає команду в контейнері; Git для ваших commit надалі виконуйте на хості, у каталозі проєкту. Якщо є `not found`, перевірте рядок `RUN apk add ...` у Dockerfile і повторіть `up -d --build`. Вивід версії підтверджує наявність утиліти, а не доступ до зовнішнього інтернету.

### P-03 Автотест, збереження й повторний запуск

Орієнтир: 20 хв активної роботи, включно з читанням кроку.

Виконайте повну перевірку, потім перестворіть стенд і повторіть її. Переходьте до наступної команди лише після успіху попередньої:

```bash replay
sh tests/check.sh pr03
sh tests/compose.sh pr03 down
sh tests/compose.sh pr03 up -d
sh tests/compose.sh pr03 ps
sh tests/check.sh pr03
```

Кожний успішний запуск має показати `CONFIG`, `SAFETY`, `IMAGES`, `TOOLS`, `PERSIST`, `RESTART`, `LOGS` зі статусом PASSED, підсумок **7/7 і 10/10**, а в кінці — `MACHINE_STAGE_OK pr03`. Для з’ясування коду завершення одразу після команди можна виконати `echo $?`: 0 означає успіх, інше значення — помилку. Новий запуск створює новий звіт; попередній не перезаписується.

PERSIST сам записує новий контрольний marker у `results/persistence.txt`, перестворює toolbox і читає той самий файл із хоста й контейнера. Усередині одного запуску значення мають збігатися, а між двома запусками — відрізнятися. Це доказ збереження через `./:/workspace`, а не резервного копіювання. RESTART сам зупиняє та запускає toolbox і перевіряє доступність Git. Додаткових ручних дій, прихованих від протоколу, для цих балів немає.

`down` прибирає контейнери й мережі; файли Dockerfile, Compose та `results/` залишаються на хості. Після `up -d` потрібний новий успішний тест. Якщо PERSIST невдалий, перевірте `volumes: ['./:/workspace']`; якщо RESTART — `CMD`, стан у `ps` та журнал. Виправте власні файли й повторіть запуск, а не редагуйте тести.

Відкрийте створений Markdown-протокол за шляхом, який надрукував тест. Якщо загубили цей шлях, прочитайте покажчик:

```bash
cat results/checks/latest-pr03.json
```

Значення `run_id` — назва каталогу останнього запуску. Його `report.md`, `assessment.json` і `junit.xml` лежать у `results/checks/<run_id>/`, журнали — у підкаталозі `diagnostics/`. Тут `<run_id>` потрібно замінити прочитаним значенням; це не буквальна назва каталогу. Поле `report` у покажчику веде до машинного JSON, а Markdown-протокол має назву `report.md` у тому самому каталозі. Markdown можна відкрити в редакторі звичайним файлом.

Крім повного архіву в results, тест автоматично оновлює `docs/reports/pr03.md` для Git. Цей файл не треба створювати або копіювати вручну. У протоколі перевірте оцінку, усі сім результатів, очікування, фактичні дані та підказки. При помилці середовища до запуску основного тесту створюються Markdown і JSON без визначеного бала; JUnit у такому випадку ще немає. Збій встановлення, доступу до Docker або завантаження не є автоматичним нулем за виконану роботу.

### P-04 Зафіксувати версію та здати роботу

Орієнтир: 10 хв активної роботи, включно з читанням кроку.

Після останньої повної успішної перевірки зафіксуйте власні конфігурації. Git-посилання є **обов’язковою умовою здачі**, а 10 балів обчислюються за контейнерними критеріями. Тест не підтверджує створення облікового запису або право володіння GitHub/GitLab-проєктом.

```bash replay
printf 'pr03\n' > STAGE
git status --short
git add Dockerfile compose.yaml STAGE docs/reports/pr03.md
git diff --cached --stat
git diff --cached
git commit -m "pr03: configure isolated toolbox"
git tag pr03
git rev-parse HEAD
```

Перед commit прочитайте підготовлені зміни. Очікуються ваші Dockerfile, compose.yaml, автоматичний docs/reports/pr03.md і за потреби STAGE; `.env` та `results/` не повинні потрапити до commit. `git commit` створює локальну версію, `git tag pr03` позначає її, `git rev-parse HEAD` друкує повний SHA. Якщо є `Author identity unknown`, виконайте налаштування автора з P-01. Якщо commit/tag цього етапу вже існують, не створюйте їх повторно.

Перевірте `origin` і надішліть поточну гілку та тег у власну копію:

```bash
git remote -v
git branch --show-current
git push -u origin HEAD
git push origin pr03
```

`git branch --show-current` має показати непорожню назву гілки. `HEAD` у команді push означає поточну гілку: вона не зобов’язана називатися `main`. Після push відкрийте власний репозиторій у браузері й перевірте файли та тег `pr03`. Якщо автентифікація не пройшла, скористайтеся офіційним маршрутом із git.md; це не Docker-помилка. Зданий тег не пересувайте й не використовуйте force push. Для виправлення створіть новий commit і новий тег `pr03-v2`, а потім надішліть саме його.

Здайте **тільки URL власного GitHub/GitLab-репозиторію**. У надісланій версії мають бути конфігурації, тег `pr03` і автоматичний `docs/reports/pr03.md` останньої успішної перевірки. Окремо надсилати протокол, тег, SHA чи URL pipeline не потрібно. Без Git-посилання робота не приймається. Ручної папки `reports/` не створюйте, `results/` не комітьте. Локальний звіт є самоперевіркою; офіційний автоматичний результат визначається перевіркою зданої версії, яку контролює викладач. Додаткова GitLab CI-перевірка пояснена в [README.md](../README.md#автоперевірки); вона не є передумовою локального запуску й не вимагається для GitHub.

Перше `check.sh` завантажує потрібні офіційні образи та збирає службову утиліту перевірки. Локальний Python установлювати не потрібно. Лише тестовий контролер отримує Docker socket, щоб виконати проби й перестворити ваш toolbox; сам toolbox socket не отримує. Службові контейнери видаляються після перевірки. У Docker Desktop вони належать до тієї самої Compose-групи `autonomous-netlab`. Побудова утиліти не замінює ваш Dockerfile.

Запитання «поясніть» і «зіставте» у роботі призначені для самоперевірки розуміння. Окремого ручного звіту, усної частки бала або прихованого додаткового завдання немає.

## 9. Типові помилки й діагностика

| Симптом | Перевірка й наступна дія |
|---|---|
| Docker Client є, Server недоступний | Запустіть Engine; у WSL перевірте Desktop integration |
| TODO, помилка YAML або невизначений BASE_IMAGE | Перевірте корінь проєкту, `.env` і `sh tests/compose.sh pr03 config` |
| Утиліта не знайдена | Виправте RUN і повторіть `up -d --build`; ручне встановлення в одному контейнері не виправляє образ |
| SAFETY невдалий | Відновіть internal control, networks, cap_drop, no-new-privileges та додатні RAM/CPU |
| PERSIST невдалий | Перевірте `./:/workspace`; потрібний файл має бути в каталозі проєкту |
| Toolbox завершується | Прочитайте `ps` і `logs`; перевірте CMD |
| Не зібралася тестова утиліта | Прочитайте `results/checks/bootstrap.log`; перевірте Docker Hub і доступ до Alpine packages |
| Немає JUnit, оцінка не визначена | Спочатку виправте передумови з report.md; основний набір перевірок ще не запустився |
| Push не вдався | Звірте origin, поточну гілку й автентифікацію за git.md |

## 10. Завдання для самостійного виконання

**Необов’язкове поглиблення, без балів:** поясніть різницю image/container/volume і спробуйте змінити лише hostname toolbox. Це не передумова наступної роботи.

Для самоперевірки назвіть один висновок, якого ваші дані не доводять, і наступну перевірку, яка змінила б рішення. Окремого файла чи додаткового домашнього налаштування не потрібно.

## 11. Зміст звіту

Звіт створюється **автоматично** командою tests/check.sh: results/checks/<run_id>/report.md. Спочатку оцінка/статус оцінювання, потім лічильники, критерії, деталі очікуваного й фактичного результату та підказки. Не створюйте окрему папку reports/ і не переписуйте помилки вручну. Тест автоматично копіює протокол у `docs/reports/pr03.md`; додайте цей файл до commit разом із конфігураціями й надішліть його до свого remote. Здайте тільки URL власного GitHub/GitLab-репозиторію. Тег `pr03` позначає версію роботи; окремі вкладення, SHA чи URL pipeline не потрібні. JSON та JUnit можна додати для діагностики. results/ не комітьте; якщо тест упав, спочатку виправте конфігурацію й отримайте новий звіт. Старий залишиться для порівняння.

ПР3–6 оцінюються автоматично по 10 балів, без усної здачі. Локальний звіт — самоперевірка; офіційна оцінка потребує контрольованого викладачем запуску.

## 12. Критерії оцінювання

| Критерій | Бали | Що перевіряється |
|---|---:|---|
| A01 | 2 | Валідний Compose і визначена побудова власного toolbox |
| A02 | 3 | Образ побудовано, потрібні інструменти працюють |
| A03 | 3 | Файл зберігається через bind mount після перестворення контейнера |
| A04 | 2 | Повторний запуск і повтор автоперевірки успішні |

Разом 10 балів. За кожний незалежний критерій зараховується зазначена кількість балів при успішній машинній перевірці; при підтвердженій невідповідності — 0 за цей критерій. Усної здачі й окремого бала за пояснення немає. Автопротокол зберігає технічні результати та підказки; власні міркування він не генерує. Збій інфраструктури означає повтор перевірки, а не автоматичний нуль. Офіційний автоматичний результат визначається перевіркою зданої версії, яку контролює викладач.

Бюджет: [45, 35, 20, 10] хв за кроками + 10 хв резерву = 120 хв. Читання, запис конфігурацій, експеримент і звіт включені. Це орієнтовний бюджет часу. Якщо активна робота перевищує 120 хв, повідомте викладачу, який крок потребував більше часу.

Після збереження результатів зупиніть поточний етап:

```bash
sh tests/compose.sh pr03 stop
```

`stop` зупиняє контейнери, зберігаючи їх і дані. Наступного разу виконайте команду `up -d` з цього протоколу. Щоб видалити контейнери й мережі, замініть `stop` на `down --remove-orphans`: файли проєкту та `results/` залишаться. Використовуйте номер **вже виконаної** роботи, щоб не читати майбутні TODO-файли.

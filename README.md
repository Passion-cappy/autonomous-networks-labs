# Мій мережевий стенд: ПР3–7

Один викладацький шаблон на весь цикл. Кожний студент створює **один власний GitHub- або GitLab-репозиторій** і продовжує його до ПР7. Тут є TODO-файли з правильними назвами, протоколи й автотести. Конфігурації стенда заповнюєте ви за протоколами. Порожній Dockerfile поки не будується — його заповнюють у ПР3.

| Робота | Протокол | Що створюєте |
|---|---|---|
| ПР3 | [docs/pr03.md](docs/pr03.md) | Власний Git, Dockerfile, базовий Compose |
| ПР4 | [docs/pr04.md](docs/pr04.md) | Мережевий Compose, HTTP-файли, HAProxy |
| ПР5 | [docs/pr05.md](docs/pr05.md) | Prometheus і Blackbox, цілі перевірок |
| ПР6 | [docs/pr06.md](docs/pr06.md) | Резерв, правила alarm і Alertmanager |
| ПР7 | [docs/pr07.md](docs/pr07.md) | Grafana, Ollama, власний AI prompt та incident report |

Початок: GitLab Fork або GitHub Import repository → clone власної копії → ПР3. Покроково: docs/git.md. Після клонування перевірте `origin`: він має вказувати на вашу власну копію.

Команди виконуються в Bash із кореня свого проєкту. Встановлення й доступ до панелей для Windows/macOS/Linux описані в [docs/platforms.md](docs/platforms.md). Другого Docker усередині контейнера не потрібно.

Почніть із [встановлення](docs/platforms.md), [Git крок за кроком](docs/git.md) та [довідника команд й імен](docs/commands.md).

## Автоперевірки

Після виконання протоколу:

```bash
sh tests/check.sh pr03
sh tests/check.sh pr04
sh tests/check.sh pr05
sh tests/check.sh pr06
sh tests/check.sh pr07
```

Кожну команду виконуйте на відповідному етапі після up потрібних сервісів. Повний `check.sh` включає потрібні експерименти відмови й відновлення; окремі допоміжні сценарії запускати не потрібно. tests/compose.sh лише вибирає список ваших Compose-файлів, без готової топології. tests/event_sink.py — приймач тестових сповіщень; tests/diagnose.py — read-only клієнт локального API. Вони є наданими засобами перевірки, програмувати їх не потрібно.

ПР3–6 мають по 10 балів, ПР7 — 12. Усі роботи оцінюються автоматично, усної здачі немає. Поглиблені завдання не оцінюються. Локальний звіт є самоперевіркою; офіційний автоматичний результат визначається перевіркою зданої версії, яку контролює викладач.

`.gitlab-ci.yml` описує додаткову перевірку на GitLab. `metadata-job` перевіряє цілісність тестів і службових параметрів, `runtime-job` запускає стенд для тегів `pr03`–`pr07` або заданого `LAB_STAGE`. Для нього потрібен runner — виконавець CI із Docker-in-Docker; якщо доступного runner немає, завдання очікуватиме в черзі. GitHub не виконує цей файл. У ПР7 такий CI-запуск пропускає LLM і дає частковий результат: повна локальна перевірка з реальною моделлю залишається обов’язковою. Налаштування runner не є студентським завданням. [Офіційний довідник GitLab CI](https://docs.gitlab.com/ci/docker/using_docker_build/).

## Образи й локальна модель

Усі зовнішні software-образи — офіційні/проектні образи Docker Hub, мають номерні теги; очікувані digest зберігаються в tests/images.lock.json і звіряються тестом. Підтримувані гілки звірено 31.10.2026. Версії не змінюйте довільно в середині перевірки; оновлення потребує повторного проходження протоколів. tests/image_audit.py читає metadata Docker Hub й повідомляє про зміну відстежуваного digest. Ця перевірка не є CVE-сканером.

Офіційний ollama/ollama:0.40.13 має приблизно 3,4 GB стисненого amd64-завантаження; це окремо від ваг моделі та оперативної пам’яті. Базовий CPU-дослід використовує qwen3:0.6b. Початкові завантаження можуть бути довгими; активне налаштування враховується окремо. Розмір образу або mem_limit не доводять мінімальну RAM ноутбука.

LLM не має інструментів керування мережею. Ви надсилаєте обмежений знімок метрик, подій і журналів окремим API-запитом. Alarm та резервування працюють і без моделі. Правильна JSON-форма не доводить правильності причин; хибні твердження потрібно спростовувати доказами.

## Здача й зупинка

Тест автоматично створює results/checks/<run_id>/report.md з оцінкою, фактичними результатами й підказками. Папки ручних reports/ немає. Тест також автоматично оновлює docs/reports/prNN.md (NN — номер роботи). Додавайте цей Markdown до commit і push разом із конфігураціями; для здачі потрібен тільки URL власного GitHub/GitLab-репозиторію. Теги pr03–pr07 позначають версії робіт; окремі вкладення, SHA та URL pipeline не потрібні; GitHub не зобов’язаний виконувати GitLab CI. Виправлення — новий тег prNN-v2. .env, results/, образи й ваги у Git не додаються. Моделі зберігаються у named volume Docker.

Зупиняйте **вже виконаний** етап. Не запускайте `pr07`, поки майбутні файли ще містять TODO:

| Остання виконана робота | Команда зупинки |
|---|---|
| ПР3 | `sh tests/compose.sh pr03 stop` |
| ПР4 | `sh tests/compose.sh pr04 stop` |
| ПР5 | `sh tests/compose.sh pr05 --profile monitoring stop` |
| ПР6 | `sh tests/compose.sh pr06 --profile monitoring stop` |
| ПР7 | `sh tests/compose.sh pr07 --profile monitoring --profile ai stop` |

`stop` зберігає контейнери й дані. Щоб видалити контейнери та мережі поточного етапу, замініть `stop` на `down --remove-orphans`. Лише для повністю виконаної ПР7 команда нижче видаляє також volume з моделлю:

```bash
sh tests/compose.sh pr07 --profile monitoring --profile ai down --volumes --remove-orphans
```

Після видалення volume модель завантажується повторно. Файли проєкту та `results/` залишаються. На кожну роботу передбачено орієнтовно 120 хв активних дій; швидкість завантаження та обсяг доступної пам’яті залежать від комп’ютера. Якщо встановлення чи виконання не вкладається в цей час, повідомте викладачу конкретний крок і помилку.

Усі сервіси та тимчасові перевірки належать одній Compose-групі `autonomous-netlab`. Тест LOGS перевіряє стани й журнали після досліду; подробиці зберігаються у `results/checks/<run_id>/diagnostics/`. Успішний `restart` ще не доводить готовності: перевірте результат відповідного тесту.
